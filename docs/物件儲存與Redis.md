# 物件儲存（MinIO／S3）與 Redis

兩者都是**可選**的。不設任何變數時，系統行為與過去完全相同：素材寫在掛載的 Volume、
快取放在各行程的記憶體、即時協作只在單一實例內同步。

設了才會啟用，而且都設計成「連不上時自動退回原本的做法」，不會因為外掛服務掛掉就整站故障。

---

## 一、物件儲存（S3 相容：MinIO／Cloudflare R2／AWS S3）

### 為什麼要用

Volume 的問題不是它會壞，而是**它跟服務綁在一起**：換部署平台、開第二個實例、
或是哪次掛載路徑設錯，素材就會不見或是分裂成兩份。物件儲存把「檔案放哪」
從「哪台機器」的問題變成「哪個 bucket」的問題，也就順便解決了多實例共用素材。

### 啟用

| 變數 | 說明 |
|---|---|
| `S3_ENDPOINT` | 端點，不含 bucket。沒帶 scheme 時自動補 `http://`（內網 MinIO 常見） |
| `S3_BUCKET` | bucket 名稱，**必須先自行建立**，本服務不會自動建 |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | 金鑰 |
| `S3_REGION` | 空＝`us-east-1`。MinIO 填什麼都行（只影響簽章） |
| `S3_FORCE_PATH_STYLE` | 空＝`1`。MinIO 必須是 1；AWS S3／R2 可設 0 |
| `S3_PREFIX` | 共同前綴，多環境共用同一個 bucket 時用來隔離 |

自架 MinIO 的人手上通常只有 `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD`，
所以 `MINIO_ENDPOINT`、`MINIO_BUCKET`、`MINIO_ROOT_USER`、`MINIO_ROOT_PASSWORD`
這組名字也一樣認得，不必改名。

### 切換步驟（順序很重要）

資料庫記的是相對路徑（`2026/08/uuid.png`），兩種後端**完全相同**，所以切換不用改資料庫。
但**舊檔不會自己搬過去**——跳過搬移就切，站上所有舊圖、旁白、成片會在切換當下集體變 404。

1. 設好上面的變數，**但先不要重啟服務**（服務仍在寫本機磁碟）。
2. 搬舊檔：
   ```bash
   DATABASE_URL=... ASSET_DIR=/data npm run assets:migrate-object-store
   ```
   可先加 `--dry-run` 看要搬什麼。這支腳本只寫入物件儲存，**不刪本機檔、不改資料庫**，
   所以隨時可以回頭。
3. 重啟服務——此時才真正切到物件儲存。
4. **再跑一次步驟 2**，補上步驟 2 到 3 之間新產生的檔案。
5. `npm run assets:verify` 確認沒有缺檔之後，才可以把 Volume 退掉。

要退回 Volume 就把 `S3_*` 變數移除再重啟；本機檔案還在原處（步驟 2 沒有刪東西）。

### 涵蓋範圍

素材、私訊附件、資料庫文件、交付包、回饋截圖、個人頭像、縮圖——全部走同一組儲存 API，
切換後端時一起換。伺服器自己要讀檔的路徑（打包交付、剪映匯出、算 checksum、產縮圖、
把 txt 素材讀進知識庫）也都改走同一層，不再直接碰本機路徑。

唯一**不走**物件儲存的是 `tmp/`：上傳一律先落地到本機暫存再串流上傳，
大檔才不會進記憶體。單檔生命週期，不需要持久。

### ⚠ 兩件配套的事

**1. 必須設 `INTEGRATION_TOKEN_SECRET`。**
Google／Notion 的 OAuth token 是加密落庫的，金鑰種子預設寫在 `STORAGE_ROOT/.integration-key`。
把 Volume 退掉之後那個檔案落在容器暫存層——**寫得進去但活不過下次部署**，
於是每次部署都換一把新種子，所有已連結的帳號會在無聲無息中全部失效且無法復原。
所以物件儲存模式下，未設這個變數時系統會直接拒絕啟用整合功能並說明原因。

```bash
openssl rand -hex 32   # 設成 INTEGRATION_TOKEN_SECRET，設一次之後不要換
```

**2. `/api/admin/backup/assets.tar.gz` 不再適用。**
那個端點打包的是本機 assets 目錄，切換後它是空的。照跑會產出一包空檔並記一筆「備份成功」，
比沒有備份更危險，所以系統會直接回錯誤。改用物件儲存自己的備份機制：
bucket 版本控管、跨區複寫，或 `mc mirror` / `aws s3 sync` 到另一個 bucket。
**資料庫仍需另外備份**——素材檔與資料庫紀錄要成對備份、成對還原。

### 運作方式

- **上傳**：multer 收到的暫存檔以串流方式 PUT 上去（大影片不進記憶體），成功後才刪暫存檔。
- **下載**：瀏覽器的 `Range` 標頭原樣轉發給物件儲存，回應（含 206／`Content-Range`）直通瀏覽器。
  影音拖進度條由物件儲存自己處理，本服務只是管道。
- **複製**（文件送進素材庫）：走伺服器端 CopyObject，不經過本服務的頻寬。
- **健康檢查**：`/api/ready` 與系統自檢都會實際寫入→讀回→刪除一個探針物件。
  只看「bucket 存在」是不夠的——金鑰權限不足時 list 會過、put 才失敗。

啟用後，Volume 相關的持久性判定與紅色警示會自動停用（素材根本不在這台機器上），
系統自檢的儲存層那一項會顯示物件儲存的端點與 bucket。

## 二、Redis

### 不設會怎樣

完全正常。單一實例部署本來就不需要 Redis。差別只有兩點：

1. 匯率、Fal 餘額這類「向外部問一次、快取一段時間」的資料變成每個實例各存一份，
   多打幾次外部 API。
2. **開到兩個以上 replica 時，即時協作會靜默失效**：房間是行程記憶體，
   甲在 A 實例、乙在 B 實例，兩人打開同一個專案卻互相看不見——沒有游標、沒有在場名單、
   一邊改了東西另一邊也不會刷新。這是「看起來有在運作、其實壞掉」的那種故障。

### 啟用

| 變數 | 說明 |
|---|---|
| `REDIS_URL` | `redis://` 或 `rediss://`（TLS）。也吃平台常見的 `REDIS_PRIVATE_URL` |
| `REDIS_PREFIX` | key 前綴，空＝`aidos`。多環境共用同一台 Redis 時用來隔離 |

### 用在哪

- **共用快取**（`server/services/cache.ts`）：兩層——先本機記憶體，再 Redis。
  Redis 掛掉時仍有本機那層，降級後只是「各實例各算一次」，不會退化成每個請求都打外部 API。
- **即時協作跨實例同步**（`server/services/realtimeBus.ts`）：
  游標／編輯指示／資料失效事件透過 pub/sub 轉給其他實例；在場名單則交換「名冊」而不是結果，
  各實例各自算出同一份 `本機 ∪ 各遠端` 的名單。
  某個實例被砍掉時，它的名冊最慢 90 秒過期（正常關機會立刻送空名冊），
  畫面上不會留著永遠不離開的幽靈協作者。

### 刻意不用 Redis 的地方

**限流**（`server/services/rateLimit.ts`）維持 PostgreSQL 交易＋advisory lock 的設計。
那是刻意的 fail-closed 架構：資料庫故障時限流會擋下請求而不是放行。
換成 Redis 會把它變成 fail-open（Redis 掛掉＝限流失效），是安全性上的退步。

### 故障時的行為

所有 Redis 操作失敗（未設定、連不上、逾時）都回 `null`／`false` 而不是拋例外，
呼叫端一律有本機退路。連線會以指數退避重試（0.5 秒起、最多 30 秒），
錯誤 log 每 30 秒最多一則，避免 Redis 全掛時淹掉整份部署 log。

系統自檢有「快取／跨實例協調(Redis)」一項：未設定顯示單機模式（不算故障），
設了卻連不上才會亮紅。
