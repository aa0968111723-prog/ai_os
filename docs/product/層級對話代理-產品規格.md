# 層級專用對話代理 · 產品規格

> 對象：產品／實作／內部培訓  
> 不含程式碼；實作須沿用既有 session、組切換、Policy／ACL、點數與審批，不得在對話層另開權限後門。

---

## 1. 目標

把「全站一個萬能聊天機器人」改成 **依目前身分掛載的專用對話代理**：

| 站內角色（關係） | 代理名稱（建議 UI） | 定位 |
|------------------|---------------------|------|
| 組員 `group member` | 組員創作助理 | 本組專案內備料、分鏡、生成、查自己的進度 |
| 組長 `group leader` | 組長產線助理 | 待審、退回建議、組內進度、母版／點數提醒 |
| 團隊管理 `team admin` | 團隊營運助理 | 跨組概況、邀請／成員、額度與門檻建議 |
| 開發者／超級管理 `isSuperAdmin` 等 | 系統級代理 | 全站診斷、設定建議、工作流／代理設計、成本總覽 |

同一使用者可在 A 組是組長、B 組是組員 → **以「目前選中的組 + 在該組角色」決定代理**，與現有組織模型一致。

---

## 2. 核心原則

1. **能看 ≠ 能默默改完** — 高風險動作要確認或走既有 step-up／審批。  
2. **工具集按層裁剪** — 組員代理不掛「調額度／邀請」等工具，降低誤觸。  
3. **上下文最小必要** — 只餵該層該看的專案／組／全站摘要；密鑰全文永不進對話。  
4. **與 ACL 同源** — 對話觸發的讀寫必須通過與按鈕操作相同的守衛。  
5. **先兩層再四層** — 優先組員＋組長（創作與審批主路徑），再團隊長與開發者。  

---

## 3. 能力矩陣（摘要）

| 能力 | 組員 | 組長 | 團隊長 | 開發者 |
|------|:----:|:----:|:------:|:------:|
| 讀本組可見專案／筆記 | ✓ | ✓ | ✓ | ✓ |
| 本專案生成／分鏡建議 | ✓ | ✓ | ✓ | ✓ |
| 查自己的待審／進度 | ✓ | ✓ | ✓ | ✓ |
| 組待審列表、通過／退回建議 | — | ✓ | ✓* | ✓* |
| 組點數／門檻提醒與調整建議 | — | ✓ | ✓ | ✓ |
| 邀請成員、跨組彙總 | — | △ | ✓ | ✓ |
| 全站設定／成本／錯誤診斷 | — | — | △ | ✓ |
| 執行高風險變更 | — | 確認 | 確認 | **二次確認** |

\* 僅限該使用者對該組／團隊確有 leader／admin 關係。  
△ = 可視產品決定只讀建議或有限寫入，仍受 ACL。

### 絕對禁止（各層共通）

- 繞過點數預估、待審門檻、專案 ACL  
- 在對話中展示 API Key、session token、他人密碼雜湊  
- 組員代理代為「通過」審批  
- 未標示身分時假裝擁有更高層權限  

---

## 4. 入口與切換

### 4.1 UI

- 單一聊天入口即可，但必須常駐顯示：  
  **`目前：{組名} · {角色}代理`**（例如：`剪輯組 · 組長產線助理`）。  
- 使用者切換組膠囊時：**更換代理人格、工具集與系統提示**，並可選清空或摘要延續對話（產品二選一，建議新組開新串以免上下文污染）。  

### 4.2 解析順序

1. 未登入 → 不提供代理（或僅公開說明）。  
2. 已登入 → 取目前 `groupId` + 該組 role；若為 team admin／super admin 再升級可用代理檔。  
3. 同一人多組：以**當前組**為準，不把其他組私有內容混進上下文。  

---

## 5. 各層上下文（建議餵給模型的範圍）

| 層級 | 應納入 | 不應納入 |
|------|--------|----------|
| 組員 | 當前專案筆記、母版骨架摘要、自己的生成／分鏡狀態、剩餘點數（個人可見範圍） | 他組專案、全站金鑰、他人私訊 |
| 組長 | 上列 + 本組待審佇列摘要、組消耗、母版合規檢查項 | 他組待審細節、系統密鑰 |
| 團隊長 | 所屬團隊各組消耗／卡住數、邀請狀態、門檻設定 | 無關團隊資料、密鑰 |
| 開發者 | 全站健康、模型／供應商錯誤率、代理計畫失敗熱點、設定項名稱 | 密鑰**值**、使用者密碼 |

## 6. 與短影音母版自動化的銜接

| 角色代理 | 在母版流程中的典型用法 |
|----------|------------------------|
| 組員 | 「依操作卡帶我填 4 格／跑 5 段」 |
| 組長 | 「列出待審、對照三看清單、起草退回原因（固定標籤）」 |
| 團隊長 | 「本週各組點數與卡住的母版系列專案」 |
| 開發者 | 「創作代理計畫哪一步常失敗、是否調整成功條件」 |

母版文件見：`短影音母版自動化-*`（PR #255 或已合併路徑）。

## 7. 高風險與確認

以下動作代理**可以建議或代填表單**，但執行須符合站內既有確認／審批／step-up（若有）：

- 通過大額生成、批次生成  
- 修改組／個人點數上限或審核門檻  
- 邀請／停用成員  
- 變更全站設定、撤銷大量 session／MCP  
- 刪除專案或大量素材  

開發者代理預設傾向 **只診斷與建議**；寫入類需明確「使用者再次確認」語意。

---

## 8. 落地順序（建議）

| 波次 | 交付 | 驗收 |
|------|------|------|
| P0 | 規格＋提示詞草稿（本 PR） | 文件與角色表對齊 auth 模型 |
| P1 | 組員代理 + 組長代理（UI 標示目前代理） | 組員無法觸發通過審批；切組換代理 |
| P2 | 團隊長代理 | 跨組彙總正確、無漏他團 |
| P3 | 開發者代理 + 高風險二次確認 | 密鑰不進對話；危險操作有確認 |

---

## 9. 非目標（本規格明確不做）

- 一個代理自動擁有「登入者全部歷史組」的混雜最高權限  
- 無審核自動對外發布  
- 以對話繞過 Policy Engine／點數／邀請制  
- 在提示詞中硬編碼真實 API Key  

---

## 10. 實作對照（給工程，非本 PR 實作）

- 角色來源：既有 `loadAuthState`／group membership／`isSuperAdmin`  
- 能力：與 `authMeCapabilities`／policyEngine 對齊，對話 tools 為其子集  
- 審計：代理觸發的寫入仍打既有 `[audit]` 與操作者 user id  
- 測試：同一 user 在組 A leader、組 B member 時工具集不同
