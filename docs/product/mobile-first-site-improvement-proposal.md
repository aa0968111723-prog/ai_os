## 0. 一句話

> **在同一條產品提議下，以手機主流程為第一優先，用固定斷點矩陣與「修完必須整份清單重跑」的反覆測試，依序完成：基線合入 → 專案頁可完成創作 → 全站表單不裁切 → 點數／錯誤可信 → PWA 安裝收尾；桌面只做回歸，不做平行大改。**

---

## 1. 為什麼需要這份總提議

### 1.1 現況矛盾

| 現象 | 影響 |
|------|------|
| 文件與路線圖很多（全站 UIUX、專案頁簡化、PWA、創作代理 CA-*） | 執行力分散，Grok Build／代理一次吞不完 |
| 2026-08-01 線上實測仍見雙輸入框、連按丟單、點數數字不一致 | 使用者主觀認定「壞掉」 |
| 手機長頁、底欄／FAB／鍵盤裁切反覆出現 | 主流程完成率低（已有 `#294` 等修復，仍需制度化驗收） |
| PWA 基線已存在（manifest、SW、安裝、推播） | 缺的是**可驗收的手機主流程 + 安裝漏斗一致**，不是另起原生 App |

### 1.2 本提議解決的問題

1. **優先級**：明確 **手機 > 可信度 > PWA 收尾 > 桌面密度**；CA 代理路線**不納入本主線**。
2. **可執行**：Wave 邊界、檔案提示、禁止事項、驗收指令清楚，可直接餵給 Grok Build。
3. **可重複驗證**：反覆測試不是附錄，而是**合入閘門**。

### 1.3 非目標

- 不上架 App Store／Google Play；不引入 Capacitor 作為本提議範圍。
- 不引入 LangGraph／CrewAI／新 agent runtime。
- 不一次重寫後端 schema／無限畫布編輯器。
- 不刪桌面功能；不「僅桌面才有生成／核准」。
- 素材持久化（Volume／物件儲存）列為**部署並行依賴**，不擋 M1／M2 合入，但總提議上線檢查必列。

## 2. 成功定義（整包完成）

| 代碼 | 指標 | 手機必過標準 |
|------|------|----------------|

## 3. 反覆測試制度（合入閘門）

### 3.1 原則

| 規則 | 說明 |
|------|------|
| **R1 雙輪視覺** | 同一 PR：第一輪找問題並修；**第二輪用完整清單重跑**。禁止「修 A 只測 A」。 |
| **R2 雙斷點** | ≤560 與 ≤820 都要過；只過 390 不算過。 |
| **R3 鍵盤輪** | 所有表單相關 PR 必須包含「focus 輸入 + 鍵盤高度」重測。 |
| **R4 桌面對照** | 每個手機 PR 結尾在 **1280×800** 走一次主路徑。 |
| **R5 失敗即重開清單** | 第二輪若出現新缺陷 → 修完後**兩輪都重跑**。 |
| **R6 PR 必填** | PR 描述必須含「測試矩陣（斷點 × 場景 × 通過/失敗）」與第二輪日期。 |

### 3.2 固定視窗矩陣

| 代號 | 尺寸 (CSS px) | 用途 |
|------|---------------|------|
| **N** | 360 × 800 | 窄手機；防溢出與裁切 |
| **P** | 390 × 844 | 常見手機；主驗收 |
| **T** | 768 × 1024 | 平板直；避免只為 390 調壞 |
| **D** | 1280 × 800 | 桌面對照回歸 |

### 3.3 自動化（每個 PR）

```bash
npx tsc --noEmit
# 依 repo 慣用 client 測試指令，例如：
npx vitest run --config vitest.client.config.ts
# 或
npm run test:client
npm run build   # 有樣式／入口變更時建議
```

有改動的邏輯必須新增或更新單元測試；若存在 `--chrome-bottom`／padding 契約測試，**不得刪除守衛**，只可更新期望值並說明。

### 3.4 手機優先手動清單（每個 Mobile PR 打勾）

複製到 PR 描述：

```text
## 手機驗收矩陣

| 場景 | 360 | 390 | 768 | 1280 |
|------|-----|-----|-----|------|
| 無橫向溢出 | ☐ | ☐ | ☐ | ☐ |
| 今日：自動化表單展開，錯誤文案與主按鈕可見可點 | ☐ | ☐ | — | ☐ |
| 專案：不展開額外卡，≤2 滑見工作台主輸入 | ☐ | ☐ | ☐ | ☐ |
| 生成確認：主按鈕 ≥44px、不被底欄擋 | ☐ | ☐ | ☐ | ☐ |
| 留言／訊息 sheet：可輸入送出；關閉後可捲 | ☐ | ☐ | — | — |
| 底欄切換：內容區底部 padding 足夠 | ☐ | ☐ | — | — |
| 鍵盤開啟：focused 欄在可視區或可捲到 | ☐ | ☐ | — | — |
| 帳號選單：安裝成 App／連結手機與電腦可達 | ☐ | ☐ | — | ☐ |
| 「稍後」安裝後，選單入口仍在 | ☐ | ☐ | — | — |

第二輪完整重測日期：____
第一輪缺陷與修復摘要：____
```

### 3.5 建議手動操作順序（主流程煙霧）

1. 清除或使用乾淨 session（或無痕）登入。
2. 今日工作台 → 展開母版／自動化相關表單 → focus 欄位 → 看是否被裁。
3. 開啟既有專案（或建一測試專案）→ 不展開「更多」→ 數滑動次數到主輸入。
4. 觸發生成確認（可不必真扣點，若環境允許用便宜模型）。
5. 開留言 sheet → 輸入 → 關閉。
6. 帳號選單 → 安裝相關項目；若有橫幅按稍後再檢查選單。
7. 將視窗拉到 1280 重複 2–4 關鍵步。

## 4. Wave 切分（全部收入本提議）

### Wave M0 — 基線收斂（0.5–1 session）

**目標：** 已開的手機／PWA／留白修復進入可依賴狀態，測試清單入庫。

| ID | 工作項 | 說明 |
|----|--------|------|
| M0-1 | 對齊開啟中的響應式 PR | 例如 `#294`（`--chrome-bottom`）；確認與本提議 S2／S3 一致，合入或標依賴 |
| M0-2 | 安裝入口行為 | 橫幅 dismiss 不得關閉帳號選單「安裝」；`canShowInstallBanner` vs `canOfferInstall` 分離（若尚未在預設分支） |
| M0-3 | Help `#help-install` | Android／iOS／電腦步驟 + FAQ；與橫幅／選單連結一致 |
| M0-4 | 本文件入庫 | `docs/product/mobile-first-site-improvement-proposal.md`（本檔） |

**反覆測試：** N／P 表單與安裝稍後；契約測試綠。  
**完成：** 預設分支上，已知裁切契約與安裝入口規則可被後續 Wave 依賴。

---

### Wave M1 — 手機專案頁主流程（最高優先 · 1–2 sessions）

**目標：** 手機「進專案就能創作」；資訊架構服從拇指熱區。

| ID | 工作項 | 依據／提示 |
|----|--------|------------|
| M1-1 | 簡易模式打磨 | 四步主線（故事→拆分鏡→生成→送審打包）；≤820 預設或極明顯入口；見簡化提案 |
| M1-2 | 完整版手機收合回歸 | ① 預設收合、留言 sheet、生成區 ≤2 滑；對齊 declutter Phase 1 |
| M1-3 | 消滅雙輸入框 | 頂部鏡射無送出之路徑移除或改為真送出；手機只留一條可執行路徑（體檢 P1-7） |
| M1-4 | 連按「存成分鏡」不丟單 | 進行中 disable／排隊 + 回饋（體檢 P1-5） |
| M1-5 | 儀表板建立專案 | 展開後 scrollIntoView 到表單（體檢 P1-6） |

**可能涉及路徑（執行時以 repo 現況為準）：**

- `client/src/pages/ProjectPage.tsx`
- `client/src/features/project-simple/*`（若已存在）
- `client/src/pages/Launchpad.tsx` 或儀表板建立表單
- 創作工作台／分鏡相關按鈕與確認流

**反覆測試加重：**

1. 第一輪：P 走簡易四步至「確認／送出」可見  
2. 修復  
3. 第二輪：N + P 完整清單 + 鍵盤  
4. 建議第三輪：T 平板直  

**完成：** 新手機使用者不展開「更多」也能知道下一步；無雙輸入誤解。

---

### Wave M2 — 全站殼層與表單防裁切（1 session）

**目標：** 今日／自動化／設定／聊天等在鍵盤與底欄下可用，不只專案頁。

| ID | 工作項 |
|----|--------|
| M2-1 | 盤點固定底欄 + sticky CTA 頁；統一 bottom padding（優先沿用 `#294` 的 `--chrome-bottom` 契約，禁止再散落 magic number） |
| M2-2 | 表單 focus → `scrollIntoView`（預留 offset）抽共用 helper，重點頁接入 |
| M2-3 | iOS 輸入字級 ≥16px（或等效）避免 focus 縮放 |
| M2-4 | Sheet／Dialog 在 `visualViewport` 變化時主按鈕仍可及 |
| M2-5 | 推播深鏈手機落地：正確區塊或 sheet（既有 `?focus=`／hash 行為回歸） |

**反覆測試：** 每修一類表單做 N／P「開鍵盤→輸入→送出」兩輪；最後抽樣三頁全清單一輪。

---

### Wave M3 — 可信度（1–2 sessions）

**目標：** 手機上看到的數字與狀態「說了算」。

| ID | 工作項 | 備註 |
|----|--------|------|
| M3-1 | 剩餘點數單一真相 | 頂欄／選單／確認卡同一計算來源（體檢 P1-1） |
| M3-2 | 點數可理解 | 今日／本週／剩餘；能對到一次生成（不必一次做完整帳簿） |
| M3-3 | 範本／供應商失敗人話 | NIM 等失敗可讀；能 fallback 則 fallback，否則停用並說明（體檢 P0-2） |
| M3-4 | 長任務文案 | 可關頁、完成推播—手機可見 |

**並行依賴（部署）：** 素材 Volume／物件儲存 — 程式可偵測非持久並警告；真正持久化屬基礎設施。

**反覆測試：** 預估 vs 實扣對帳兩輪；故意失敗路徑一人話檢查。

---

### Wave M4 — PWA 應用程式化收尾（0.5–1 session）

| ID | 工作項 |
|----|--------|
| M4-1 | 安裝漏斗時機：不煩、不藏入口 |
| M4-2 | Help 安裝／推播步驟與 NotificationSettings 文案一致 |
| M4-3 | `display-mode: standalone` 安全區再驗 |
| M4-4 | 更新橫幅：編輯中不強制重整（APP-00 行為回歸） |

**反覆測試：** 瀏覽器分頁 vs 主畫面圖示各一輪；iOS 照 Help 走通（有真機時）。

## 6. 工程硬規則（Grok Build／代理必守）

1. **一 Wave 一分支一 PR**；標題建議：`docs|fix|feat(mobile): M{n} …`。
2. **禁止**為手機刪桌面功能；桌面行為變更必須在 PR 說明並過 D 對照。
3. **禁止**無必要 migration／新表；優先 CSS 變數、既有 localStorage、既有 tRPC。
4. **禁止**引入新 agent 框架。
5. **禁止**刪除既有契約測試後不重建等價守衛。
6. PR 描述**必須**含測試矩陣與第二輪重測紀錄。
7. 測試失敗不得用「桌面看過沒問題」帶過。

## 8. 風險與回退

| 風險 | 緩解 |
|------|------|
| 修手機 padding 弄壞桌面 | R4 強制 1280 對照；契約測試 |
| 多 PR 並行改同一 `styles.css` | M0 先合留白契約；後續 PR rebase |
| 點數公式改動引發爭議 | M3 先統一「剩餘」定義並在 Help／選單註明；保留舊欄位只讀若需要 |
| 部署級 P0（素材）未解 | 總提議驗收清單單獨勾「基礎設施」；不與 M1 綁死合併 |

回退：各 Wave 獨立 PR，可 revert 單一 Wave；避免巨型混合 commit。
