## 定案（2026-08-07）

| 題 | 決定 | 後果 |
|---|---|---|
| 1. 基金會法人身分？ | **不確認** | **Remotion 出局**。全案走全開源堆疊（mediabunny，MPL-2.0），零法務懸念 |
| 2. 要不要真 MP4？ | **要** | 走瀏覽器 WebCodecs；伺服器 ffmpeg 暫不做（理由見下） |
| 3. 使用者是誰？ | **會用剪輯軟體，但需要剪初稿／快速預覽給夥伴組員** | 見下方「這句話改了什麼」 |

### 第 3 題改了什麼

原報告把「多軌／BGM／轉場」放在路線 B 的核心。**這是錯的優先順序。**

既然精修仍在 Premiere 完成，那些在 NLE 裡做更快更好，剪輯台重做一次只是劣化版。
真正卡住使用者的是另外兩件事：

1. **修剪做不到** — 「剪初稿」的字面意思就是切 in/out，而 `scenes` 現在連 sub-second 都存不了
2. **沒有能丟給夥伴看的東西** — 交付包要對方會開 Premiere 才看得懂

而且「快速預覽給夥伴」意味著 MP4 只需要**預覽畫質**，不是母帶。這讓瀏覽器 WebCodecs 完全夠用，
**伺服器 ffmpeg 可以整個不做**（原報告的「後路」在這個用途下是過度設計）。

修正後的優先序：**修剪 → 出可分享的 MP4 → （若真有需要再談）多軌**。

## 2. 缺口分析：為什麼現在還不算「剪輯台」

1. **時間精度**：`durationSec` 是 `integer` 秒。剪不出 3.5 秒，也沒有 in/out 點——
   一段 8 秒的生成影片，現在只能整段用或整段不用。
2. **軌道**：一鏡＝一個畫面。**跨鏡的背景音樂無處可放**，字卡／浮水印／轉場也沒有容身之處。
3. **修剪**：`scenes` 沒有 `trimStart`／`trimEnd`，素材長度與鏡長不一致時只能重生成。
4. **預覽**：`StoryboardPlayer` 一次只掛一個 `<video>`，換鏡即換 src。
   沒有整片時間軸 scrub、沒有波形對位、沒有 J/K/L。
5. **輸出**：全站沒有任何一條路徑產出 MP4。交出去的是「請你自己去 Premiere 組」的交付包。

> 缺口 1–3 是**資料模型**問題，缺口 4 是 **UI** 問題，缺口 5 是**基礎設施**問題。
> 三者成本差一個數量級，所以下面拆成三條路線分開決策。

## 4. 三條路線

| | **A. 強化預覽台** | **B. 真時間軸＋瀏覽器輸出** | **C. Fork 現成編輯器** |
|---|---|---|---|
| 做什麼 | 把 `StoryboardPlayer` 升級成合格的預覽台 | 引入獨立時間軸模型＋canvas 合成＋WebCodecs 出 MP4 | fork OpenCut／openvideodev 接進來 |
| 資料改動 | `scenes` 加 `trimStartMs`／`trimEndMs`／`volume` | 新增 `timelines`／`timeline_tracks`／`timeline_clips` | 對方的模型，需雙向同步 |
| 新相依 | **0**（wavesurfer 可選） | mediabunny（MPL-2.0） | Next.js／Tailwind／shadcn／Zustand／PixiJS |
| 規模 | 小（~2 週） | 中（~4–6 週） | 大且持續（追上游） |
| 風險 | 低 | 中（WebCodecs 覆蓋率，見 §7） | **高**：技術棧全衝突、違反 ADR-009 邊界紀律、授權地雷 |
| 交付 | 「剪基本預覽畫面」✅ | 「專業度」✅ | — |

### 建議：**A → B，不要 C**

C 被否決的具體理由，不是「不夠好」而是**接不上**：

1. 本站是 Vite ＋ wouter ＋ 自製 design tokens；OpenCut／openvideodev 都是 Next.js ＋ Tailwind ＋ shadcn。
   接進來等於在同一個 bundle 裡養兩套設計系統，`check:ui-primitives` 那條守門線會直接崩掉。
2. `ADR-009 Import Boundary` 明確規範三層依賴方向。外來編輯器的 store／service 不會遵守。
3. openvideodev 的 >3 員工付費條款、Twick 的 SUL，都需要法務判斷才敢動。
4. OpenCut 雖然 MIT 最乾淨，但**正在往 Rust 重寫**，現在 fork 就是綁定一個會消失的上游。

**但 C 的程式碼仍然要讀**——尤其 Twick 的模組切分（timeline model／canvas／render 三者解耦）
和 openvideodev 的 WebCodecs 匯出流程，是路線 B 最好的施工圖。

## 5. 「專業度」的驗收清單

把抽象的「專業度要出來」翻成可勾選的條目。**這八點做到，就不是玩具。**

| # | 項目 | 具體標準 | 現況 |
|---|---|---|---|
| 1 | **時間用整數，不用 float** | 位置／長度一律存整數毫秒或影格（@30fps），禁止累加浮點秒 | `exporter.ts` 已經這樣做，**app 模型還沒有** |
| 2 | **影格級 scrub** | 拖時間軸游標，畫面即時跟到該影格；`←/→` 一格、`Shift+←/→` 一秒 | ❌ |
| 3 | **音訊分軌＋增益＋旁白閃避** | 旁白／音效／環境音／BGM 各自一軌，可獨立調音量；旁白出現時 BGM 自動 ducking | FCPXML 的 lane -1/-2/-3 已經是這個結構，**UI 沒有暴露** |
| 4 | **鍵盤優先** | `Space` 播停、`J/K/L` 倒退/停/快進、`I/O` 標入出點、`S` 切割 | ❌ |
| 5 | **安全框** | 依 `FormatPicker` 的 16:9／9:16／1:1 切換 title-safe 輔助線 | ❌（格式選擇器已有） |
| 6 | **缺素材優雅降級** | 素材 404 時顯示佔位並照常走時間軸，不卡住 | ✅ `StoryboardPlayer` 的 `brokenUrl` 已實作 |
| 7 | **往返一致性** ⭐ | **剪輯台剪出來的結果，必須原封不動長進 FCPXML／XMEML／剪映草稿包** | ❌ — 這是「串接」的核心 |
| 8 | **可稽核** | 剪輯動作進事件流，與審批三態機同一條時間線 | ❌ |

> **第 7 點是整份報告最重要的一句話。**
> 若剪輯台自己有一套模型、匯出又走 `scenes`，就會出現「預覽裡剪好的版本，交付包裡不是那個版本」——
> 這是所有半吊子剪輯功能的死法。
> 正確做法：**單一時間軸模型，同時餵預覽器與所有 exporter**。
> `exporter.ts` 的 `TimelineScene` 型別已經是很接近的中介表示，應該把它抽到 `shared/` 成為共用契約。

## 6. 資料模型建議

**不要動 `scenes`。** 分鏡、審批三態機、交付包、短影音母版全部掛在它上面，動它風險過高。

改為**在 `scenes` 之上長出時間軸**：專案第一次開剪輯台時，由 `scenes` 一次性生成 timeline，
之後兩者獨立演化（timeline 記得自己來自哪些 scene，可重新同步）。

向 OTIO 看齊的型別草案（**尚未落地，僅供討論**）：

```ts
// shared/timeline.ts — 預覽器與所有 exporter 共用的單一真相
export type Frames = number;              // 整數影格 @ TIMELINE_FPS(30)，禁止 float 秒

export type TimelineClip = {
  id: string;
  sceneId: string | null;                 // 來自哪一鏡；null＝剪輯台自己加的（字卡、BGM）
  assetId: string | null;
  kind: "video" | "image" | "audio" | "text";
  start: Frames;                          // 在軌道上的位置
  duration: Frames;
  sourceIn: Frames;                       // 素材內修剪起點（缺口 3）
  gain: number;                           // 0..2，預設 1
  transitionIn?: { kind: "cut" | "fade"; duration: Frames };
};

export type TimelineTrack = {
  id: string;
  kind: "video" | "narration" | "sfx" | "ambience" | "music" | "subtitle";
  lane: number;                           // 直接對應 FCPXML 的 lane（-1 旁白／-2 音效／-3 環境音）
  muted: boolean;
  clips: TimelineClip[];
};

export type Timeline = {
  fps: 30;
  width: number; height: number;          // 由 FormatPicker 帶入
  tracks: TimelineTrack[];
};
```

`lane` 欄位刻意與 `buildFcpxml` 現有的 lane 配置對齊——這樣 §5 第 7 點（往返一致性）
不需要任何轉換邏輯，exporter 讀 `Timeline` 就能直接產出目前品質的 FCPXML。

## 7. 真 MP4：三個選項

| 選項 | 成本 | 風險 | 判斷 |
|---|---|---|---|
| **瀏覽器 WebCodecs**（mediabunny `CanvasSource`） | 零伺服器成本 | WebCodecs 全球覆蓋 **~95.5%**；Safari **26+ 才完整支援**、**Firefox Android 不支援**、Firefox 各平台**不支援 AAC 編碼** | 🟢 主線，但**必須偵測能力並明確擋掉**不支援的瀏覽器 |
| **伺服器 ffmpeg** | 映像要裝 ffmpeg（alpine 約 +80MB）、吃 Zeabur CPU 與時間預算 | 長片會壓住容器 | 🟡 當後路：長片／瀏覽器不支援時走這條，**直接重用 `exportJobs` 的 job＋advisory lock＋輪詢骨架** |
| **不做，維持交付檔** | 零 | 剪輯師仍要開 Premiere | 🟡 完全合理的選擇——取決於 §10 的第 2 題 |

建議：**瀏覽器優先、伺服器後路**，而且第一版可以先只做「輸出預覽用的低碼率 MP4／WebM」，
正式成片仍走 NLE。這樣既有「看得到成品」的體感，又不用馬上背伺服器算圖的成本。

| ~~5~~ | ~~多軌／BGM／轉場~~ | — | **暫不做**（在 Premiere 完成，見「定案」） |

順序調整的理由：原本 PR 2 是預覽台、PR 3 才是修剪。但第 3 題的答案是「剪初稿」，
**修剪才是被卡住的動作**，預覽台是輔助它的介面。先給能力，再給介面。

### PR 1 實際做了什麼（已完成）

原計畫是「抽型別＋轉換函式」，實作時發現有更該先修的東西：

`buildSrt`／`buildFcpxml`／`buildXmeml`／`buildEdl` **各自維護一個時間累加器**——
srt 與 edl 累加浮點秒，fcpxml 與 xmeml 各自把秒換算成影格。四者目前巧合一致，
因為 `durationSec` 是整數；**一旦加上修剪（必然 sub-second），浮點那兩份就會與影格那兩份漂開**，
而且是隨鏡數累積放大的漂移（0.1 秒 × 100 鏡：浮點得到 9.99999999999998，影格得到 10）。

所以 PR 1 收斂的是**時間**，不是型別：邊界一律先算成整數影格、秒數再從影格推回，
四種格式與站內預覽共用同一份 `layoutTimeline()` 結果。在加修剪**之前**做，正好擋掉整類 bug。

順帶修掉一處既有落差：`sceneDur`（交付）對無效鏡長退回 **3 秒**，
`StoryboardPlayer` 的 `clampDur`（預覽）卻是 clamp 成 **1 秒**——同一個 `durationSec=0` 的鏡，
預覽播 1 秒、交付包排 3 秒。API 有 `min(1)` 擋著所以是舊資料才踩得到的潛在落差，
但「預覽看到的不是交付出去的」正是 §5 第 7 點要根除的病。

刻意**沒做**的事：多軌資料模型。目前沒有需求（多軌在 Premiere 做），
為了「架構完整」先長出來只會變成沒人用又要維護的抽象。

### PR 2 實際做了什麼（已完成）

`scenes` 新增 `trim_start_ms`／`trim_end_ms`（migration 0040），採 NLE 慣用的
**「來源入點＋時間軸長度」**模型，不是「頭尾各切掉多少」——素材重新生成、長度變了的時候，
絕對出點仍指向素材上的同一個時間點，相對切法會跟著飄。
`trim_end_ms` 為 null＝未修剪，舊分鏡行為完全不變（有逐字比對的回歸測試釘住）。

修剪貫穿**全部五種交付格式**，各自寫在對的欄位上：

| 格式 | 修剪寫在哪 |
|---|---|
| FCPXML | `asset-clip` 的 `start`（來源入點）；`asset` 宣告長度改取「入點＋鏡長」 |
| Premiere XML | `<in>/<out>`（素材取用範圍），`<start>/<end>` 仍是時間軸位置 |
| EDL | 前兩個時間碼（來源進出點） |
| SRT | 字幕跟著修剪後的鏡長 |
| 剪映草稿 | `source_timerange.start`；素材 `duration` 同樣改取「入點＋鏡長」 |

過程中又挖出 PR 1 沒清乾淨的三個獨立時間累加器：`jianying.ts`（第五個）、
`buildVoiceoverSrt`（第六個）、以及**鏡頭表的時間碼**（第七個）。
最後那個特別要命——剪輯師照著鏡頭表對位，它報未修剪的長度就會整片錯開。全部併進 `layoutTimeline()`。

另修掉 `msToFrames` 的浮點精度問題：`(ms / 1000) * 30` 在 2050ms 會算出 61.4999…
（2.05 在 IEEE754 沒有精確表示），四捨五入掉到 61 影格。改成先乘後除。

**沒做**：波形（wavesurfer）。它是新相依，而且真正的用途是配合全片 scrub 對位，
歸在 PR 3 的預覽台比較合理——現在單放一個波形圖沒有東西可以對。
