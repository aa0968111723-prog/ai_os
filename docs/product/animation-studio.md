# 動畫創作室（Animation Studio）

> 路由：`/studio`（挑專案）、`/studio/:projectId`（創作室本體）
> 程式：`client/src/features/animation-studio/`、`client/src/pages/AnimationStudioPage.tsx`

## 這一頁在解什麼

分鏡的第一版幾乎都是手畫的——構圖、鏡位、人物走位在腦裡是圖不是字。
站內原本只有「文字提示詞 → 生成」這條路，於是那張草圖只能畫在紙上、拍照、上傳，
再用文字把它重講一次。創作室把這一段收進站內：

**手繪大白板**（畫）→ **順序分鏡表**（排）→ **AI 協作欄**（把畫面變成文字、把手稿變成分鏡畫面）

## 三個區塊與兩種版面

| 區塊 | 桌機 | 手機輕量版（≤820px 或觸控 ≤1100px） |
| --- | --- | --- |
| 手繪大白板 | 中央，常駐 | 中央，常駐（其餘面板讓位） |
| 筆刷櫃 | 左側直欄，含手感微調 | 底部橫向 dock，只留粗細／濃度／顏色 |
| 順序分鏡表 | 底部橫向軌道，可拖曳重排 | 貼底 sheet（點「分鏡」叫出），只用箭頭重排 |
| AI 協作欄 | 右欄；<1180px 收成右側抽屜（**仍叫得出來**） | 貼底 sheet（點「AI」叫出） |

版面決策的單一真相是 `studioLayout.ts` 的 `resolveStudioLayout()`，算出來後以
`data-mode`／`data-ai` 掛在根節點上交給 CSS。**CSS 不得再用 media query 決定版面**——
輕量版的條件是「窄 **或**（觸控 且 ≤1100px）」，media query 寫不出第二個條件。
（實測災情：960px 的觸控裝置上 JS 判定輕量版、CSS 卻套桌機三欄，白板被擠進 200px 的
側欄格只佔畫面 21%，筆刷櫃直向鋪滿整頁。修好後同一台裝置白板佔 96%。）
**輕量版不只是把面板藏起來**，它同時降低白板的實際成本：

| 預算 | 桌機 | 輕量版 |
| --- | --- | --- |
| 筆畫上限 | 1200 | 400 |
| 復原步數 | 60 | 20 |
| 匯出長邊 | 2048px | 1280px |
| 渲染 DPR | ≤2 | ≤2 |

（DPR 3 的手機畫滿版白板是四倍像素成本；沒有筆畫上限的話，低階機愈畫愈頓。
桌機上限 1200 是與本機存檔預算對齊的結果，見下方「效能」。）

## 效能：三個會讓人覺得「網站很盪」的地方

這一頁是站內唯一「每秒幾十次事件 × 每次都要重畫」的介面，所以三條路徑都特別處理過。

### 1. 其他頁面完全不受影響（實測）

| | 加創作室前 | 加之後 |
| --- | --- | --- |
| 主 JS（gzip） | 107.51 KB | 108.31 KB（+0.8 KB，只有新圖示） |
| 主 CSS（gzip） | 35.84 KB | 35.84 KB |

創作室的程式與樣式是獨立 chunk（JS 14.6 KB／CSS 2.5 KB gzip），點進 `/studio` 才下載。

### 2. 落筆與縮放：重畫成本與筆畫數脫鉤

| 情境 | 做法 |
| --- | --- |
| 正在畫的那一筆 | 畫在獨立的 live 層，每次 pointermove 只重畫這一筆 |
| 放手提交一筆 | **只把新的那筆疊上去**，不整份重畫（`raster("auto")` 的追加判定） |
| 縮放／平移途中 | **完全不重畫**，用 CSS transform 搬既有點陣圖；停下 140ms 後才重新光柵化一次 |
| 復原／換鏡／換尺寸 | 整份重畫（使用者發起、偶爾為之） |

第三條是關鍵：兩指縮放每秒發出幾十次檢視變更，每次都重走整份筆畫就是「一縮放整個卡住」。
位移貼圖交給 GPU，成本與筆畫數無關；代價只有縮放途中那一下略糊，手放開就變清楚。
（橡皮擦是直接挖已提交的那一層，所以**落筆前**會先把待重畫的補完，否則擦痕會整片偏掉。）

### 3. 存檔：抽稀 × 壓縮格式，體積少 92%

原本每 600ms 一次的自動存檔會同步 `JSON.stringify` 整份文件——那是會卡住主執行緒的。
兩個改動疊起來（實測，400 筆的白板）：

| | 存檔體積 | serialize 耗時 |
| --- | --- | --- |
| 原本（物件形狀、不抽稀） | 2.39 MB | 40 ms（手機約 3–5 倍） |
| 抽稀 + 扁平三元組 | **0.18 MB** | **6.0 ms** |

- **抽稀**（`simplifyStroke`，RDP 容差 0.75px）：只在放手時做一次，畫的當下每個取樣點都照用。
  實測共線冗餘點佔 84%——它們對畫面毫無貢獻，卻同時吃體積與重畫成本。
- **壓縮格式**：點存成扁平三元組 `[x,y,p,…]` 並取整（0.1px／0.01）。白板長邊 1600px，看不出差別。
- **先估再存**：`estimateBoardBytes` 不做序列化就估出大小，超過 `MAX_BOARD_BYTES`（1.2 MB）直接不存，
  不白卡主執行緒一次。桌機上限 1200 筆 ≈ 0.55 MB，在預算內。

## 全螢幕專注模式

工具列最右邊的 ⛶（快捷鍵 **F**）進沉浸模式：頂欄、底部分頁列、私訊小球、回饋浮標
全部讓開，創作室覆蓋整個視窗。實測白板高度佔比：手機 48% → **76%**、平板 61% → **78%**。

兩層實作（`useImmersive.ts`）：原生 Fullscreen API 會連瀏覽器介面一起吃掉；
**iOS Safari 不支援對元素 requestFullscreen**，所以 CSS 沉浸那一層一定成立——
不然 iPhone 使用者按下按鈕會完全沒反應。退出的三條路（按鈕、Esc、系統手勢）
都收斂到同一個狀態，`fullscreenchange` 有接。

災情大又難重現，所以那條有獨立的測試盯著。

## 白板怎麼運作

三層堆疊，這是「描圖」與「橡皮擦」能同時成立的原因：

```
① 紙面（白色方框，CSS）
② 參考圖 <img>（這一鏡目前的畫面，可切換顯示）
③ 筆畫 canvas（透明）＋ live canvas（正在畫的那一筆）
```

橡皮擦用 `destination-out` 只挖掉第三層，露出紙面與參考圖；
若把參考圖畫進 canvas，擦線條會把描圖底稿一起擦掉。

正在畫的一筆只重畫它自己（live 層），所以白板上已有幾百筆時，筆跡延遲仍是常數。
橡皮擦例外——它要挖的是已提交那一層，所以直接畫在 base 上。

### 筆刷

六支內建（鉛筆／簽字筆／毛筆／麥克筆／噴槍／橡皮擦），參數化的筆跡數學全在
`brushes.ts`：壓力→線寬、速度→飛白、收筆漸細、顆粒抖動、等距取樣。
顆粒與噴濺是**決定性**的（由筆畫 id ＋ 點序號推導），否則每次縮放重繪畫面都會抖。

沒有壓感的裝置一律以 0.5 計（`normalizePressure`）——直接用 `pressure=0` 會畫出
一條看不見的線，是「我畫了但沒東西」最常見的成因。滑鼠與手指改用速度近似壓力。

### 收錄筆刷

心智模型一條：**內建筆刷是範本，收藏的筆刷是你的**（規則在 `brushCollection.ts`）。

- 調整內建筆刷 → 只影響這次落筆，換一支再換回來仍是原本的手感
- 收錄 → 存成一支屬於你的筆（上限 24 支）
- 調整自己的筆 → 直接記住

## 草稿存在哪裡

白板草稿存 localStorage，每個「專案 × 分鏡」一份（`_free` 是還沒選分鏡時的自由塗鴉）。
理由與代價：

- 塗鴉階段不該打擾團隊素材庫，也不該讓每一筆都等網路
- 代價是**綁裝置**：手機畫的不會出現在電腦上，UI 有明講
- 空間滿了**只犧牲「自由塗鴉」那一份暫存**，絕不動其他鏡的草稿——為了存這一鏡而
  默默刪掉別鏡畫好的東西，是把資料遺失偽裝成復原。仍失敗就顯示「本機草稿空間已滿」，
  絕不默默丟掉（畫面上還在、其實沒存到，是最傷的失敗模式）

存檔在停筆 600ms 後寫入，離開創作室時再補存一次。
切換分鏡時「舊分鏡 id 配上新白板」這個經典覆蓋 bug 由 `useBoardSession.test.ts` 盯著。

## 已知界線

- 草稿不跨裝置同步（見上）。要跨裝置就是「存成這一鏡的畫面」。
- 白板是筆畫向量，不支援匯入圖層或貼圖；描圖底稿只有「這一鏡目前的畫面」。
- 復原是「整份重畫」，在接近上限（1200 筆）時會有一次明顯的停頓。要根治得做週期性
  快照（每 N 筆存一張點陣圖，復原時從最近的快照往前補），目前判斷不值得那個複雜度。
- 存檔用 localStorage（同步、全網域共用約 5MB）。若之後要支援更大的畫，正解是換 IndexedDB
  （非同步、配額大得多），存取層已收斂在 `studioStorage.ts`，換掉不影響呼叫端。
- 匯出 PNG 只含紙面與筆畫，**不含**描圖底稿——那張是拿來描的，烘進去會分不清哪張是手稿。
- 環境音在這裡**只編描述、不生成**。生成要挑音效模型、預估點數、試聽，那是分鏡表
  單格工作室「環境音」分頁的職責，不在創作室重做一套。
