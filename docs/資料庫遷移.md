# 資料庫遷移與基準採用 Runbook

本專案採 **migration-first**。正式環境只有 release／one-off job 可以變更 schema；Web
應用啟動只會讀取 migration ledger 並計算 schema drift，絕不自動 `push`、刪資料或建索引。

## 一、三個安全命令

| 命令 | 是否寫入 DB | 用途 |
|---|---:|---|
| `npm run db:check` | 否 | 驗證 migration hash／連續性，並以唯讀方式計算 live schema drift |
| `npm run db:migrate:dry-run` | 否 | 顯示空 DB／已納管 DB 尚待套用的 migration 與 hash |
| `npm run db:migrate` | 是 | 取得 PostgreSQL advisory lock，交易式套用待辦 migration |
| `npm run db:adopt:dry-run` | 否 | 檢查既有未納管 DB 是否與目前 schema **完全相符** |
| `npm run db:adopt -- --confirm=<fingerprint>` | 只寫 ledger | 將結構已相符的既有 DB 明確 baseline；不執行 public schema DDL |
| `npm run db:adopt:dry-run -- --through=0001_managed_indexes` | 否 | 一次性驗證舊 runtime-push DB 僅缺 0002/0003 的純新增 DDL |

所有命令都需要 `DATABASE_URL`。輸出只顯示使用者、host、port、database，不顯示密碼。

## 二、全新空資料庫

先用與正式服務相同 commit／映像執行：

```bash
npm run db:migrate:dry-run
npm run db:migrate
npm run db:check
```

`db:migrate` 會建立 `drizzle.__drizzle_migrations`，按 `drizzle/meta/_journal.json` 順序套用
SQL，最後再比對 `server/db/schema.ts`。任一步失敗時命令為非零 exit；應用服務不要啟動。

## 三、既有資料庫第一次納管

這是一次性的 transition，不能用 `db:migrate` 猜測既有結構。

1. 暫停新部署，先做 `pg_dump -Fc`；涉及素材路徑的版本也同步備份 `/data`。
2. 用新映像連到既有 DB 執行 `npm run db:adopt:dry-run`。
3. 確認輸出 target 是正確的 host/database，且 `schema drift: none`。
4. dry-run 會輸出本次 migration 集合的 fingerprint；原樣帶入：

   ```bash
   npm run db:adopt -- --confirm=<dry-run 顯示的 fingerprint>
   npm run db:check
   ```

5. `adopt` 在 advisory lock 下重新檢查一次，然後只建立 `drizzle` ledger 並記錄目前所有
   migration。它不會重跑初始建表 SQL，也不會改 public tables/data。

### 本版一次性 legacy 0001 bridge

舊正式庫若由過去的 runtime `pushSchema` 建立，會正確顯示只缺
`0002_distributed_rate_limits` 與 `0003_idempotency_records`。此時不能把最新版 ledger
全寫成已套用，也不能直接跑 `db:migrate`；使用受限 bridge：

```bash
npm run db:adopt:dry-run -- --through=0001_managed_indexes
npm run db:adopt -- --through=0001_managed_indexes --confirm=<dry-run 顯示的 adoption token>
npm run db:migrate
npm run db:check
```

bridge 不是任意 `--through` 後門。程式只接受 `0001_managed_indexes`，並要求 Drizzle 回報
`hasDataLoss=false`、零 warning，且 live schema 的**全部** drift 必須逐字正規化後正好等於
0002/0003 的 2 張新表與 3 個索引。它先只記錄 0000/0001，讓正常 migrator 再交易式套用
0002/0003。多一欄、少一索引、其他 drift、未來多出 migration 都會 fail closed。

若一般 dry-run 或 bridge 顯示非預期 drift，**不得 baseline**。先在還原的正式備份副本診斷 SQL。常見舊版缺口是
`group_options_group_type_value_uq`、`feedback_user_group_uq`、
`generations_active_idx` 或 `generations_project_active_idx` 未成功建立；migration
`0001_managed_indexes.sql` 內有明確的去重規則，但對既有未納管 DB 執行前仍須先查出重複列、
確認保留策略與備份可還原，不要直接複製到正式庫盲跑。

## 四、日常 schema 變更

1. 修改 `server/db/schema.ts`。
2. 產生 migration：

   ```bash
   npm run db:generate -- --name=short_description
   ```

3. 審查新 SQL；特別搜尋 `DROP`、`ALTER TYPE`、`SET NOT NULL`、`UNIQUE` 與大表 rewrite。
4. 在「正式備份還原副本」跑 `db:migrate:dry-run`、`db:migrate`、測試與 `db:check`。
5. migration SQL 與 `meta` 一起 commit。**已在任何共享環境套用的 migration 絕不可修改**；
   ledger hash 不符時服務會 fail closed，修正方式是新增下一份 migration。
6. 先執行 release migration，再滾動啟動新應用版本。不要讓每個 replica 各自 migrate。

大型／危險變更採 expand → backfill → contract：

- 版本 A 新增 nullable 欄／新表，舊程式仍可運作。
- 背景批次回填並監控。
- 版本 B 切讀寫到新結構。
- 確認一個完整保留週期後，版本 C 才刪舊結構。

本 migrator 以 PostgreSQL transaction 套用 migration；不要在其中使用
`CREATE INDEX CONCURRENTLY`（PostgreSQL 禁止在 transaction block 中執行）。超大索引應寫
獨立、可重入的維運 runbook，完成後再以小 migration 收斂 schema/ledger。

## 五、部署順序

正式映像的 `start.sh` 會先跑唯讀 `db:check`。遇到空 DB、pending migration、ledger hash
錯誤或 schema drift 時以 exit 78 停止，避免不相容程式接流量。

推薦 release job（同一映像、單一實例）：

```bash
npm run db:migrate:dry-run &&
npm run db:migrate &&
npm run db:check
```

成功後才啟動／滾動 App replicas。若平台沒有 release phase，先以 one-off shell/command
執行上述流程；不要把 `npm run db:migrate` 塞回 Web `startCommand`。

## 六、失敗與回滾

沒有通用的自動 down migration；資料庫回滾必須依變更性質決定：

- **migration 尚未提交**：PostgreSQL transaction 會回滾該批 SQL；查 log、修正後新增或在
  尚未共享的本地 migration 修正，再重跑。
- **migration 已提交、應用部署失敗**：優先回滾到仍相容新 schema 的前一版應用，或新增
  forward-fix migration。expand/contract 的目的就是保留這條路。
- **已提交的破壞性變更／資料錯誤**：停止所有寫入，從 migration 前的 `pg_dump` 還原到新 DB，
  若資料與素材引用一起變動則同步還原同時間點 `/data`，驗證後切換連線並部署舊 commit。
- **baseline 採用錯誤但其後尚未套用新 migration**：確認只需撤銷納管紀錄後，可備份並執行
  `DROP SCHEMA drizzle CASCADE`；這不碰 public tables。若 adopt 後已套用新 migration，
  不可只刪 ledger，必須按該 migration 的 forward-fix／備份還原處理。

每次危險 migration 的 PR 都要附：備份時間、還原命令、預估鎖表時間、舊版應用相容性、
驗證查詢與明確停止條件。
