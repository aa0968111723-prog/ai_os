# 資料庫系統（個人 → 組 → 團隊 → 組織）

回答「可以建構一個個人／團隊／專案、甚至到最後大型組織的資料庫系統，並且連結工作台、權限系統、AI 代理系統嗎？」——可以，而且不必另起爐灶：本系統的組織模型（超管 → 團隊 → 組別 → 個人）本來就是一棵權限樹，自訂資料庫直接掛在這棵樹的四個層級上。

## 一、這是什麼

「資料庫」＝欄位自訂的輕量結構化資料表（想像極簡版 Airtable）：

- **欄位自訂**：文字／數字／單選／日期／勾選／網址／成員 七種型別，必填可設，隨時增修欄位（不動 DB schema——欄位定義存 `data_tables.fields` jsonb，列資料存 `data_rows.data` jsonb）。
- **四層範圍**（建立時選定）：

| 範圍 | 誰看得到 | 誰能寫列 | 誰能管理（改欄位／刪庫） | 典型用途 |
|---|---|---|---|---|
| 個人 personal | 只有本人（超管也看不到） | 本人 | 本人 | 私人待辦、靈感清單 |
| 組 group | 組成員 | 成員（可鎖為僅管理者） | 組長以上、建立者 | 器材借用表、拍攝名單 |
| 團隊 team | 團隊所有組的成員 | 成員（可鎖） | 團隊管理員、建立者 | 跨組資源表、聯絡簿 |
| 全站 global | 所有登入者 | 成員（可鎖） | 超管（建立也限超管） | 全組織公告、共用字典 |

- **memberWritable 開關**：組以上範圍可切成「唯讀共享」——成員看得到、只有管理者能寫，適合公告類資料。
- **專案層級呢？** 專案已有專用結構化資料（分鏡、素材、知識庫、角色卡），v1 刻意不再加「專案範圍資料庫」避免重複；專案相關清單放組範圍、名字對上專案即可。要加時只是 `scope` 多一個值＋ACL 多一個 case。

## 二、與三大系統的連結

### 1. 權限系統（單一真相：`server/services/databaseAcl.ts`）

不另設角色。`resolveTableAccess(auth, table)` 把既有 `AuthState`（組成員/組長/團隊管理員/超管）換算成 `{canRead, canWriteRows, canManage}`：

- tRPC（網頁）與 MCP（外部 AI 代理）**走同一個函式**，不會出現「網頁擋了、AI 繞過去」。
- 無讀取權一律回「找不到」而非「無權限」——不洩漏個人庫／他組庫的存在性。
- 所有 mutation 照舊進 `audit_log`（tRPC 中介層自動記；MCP 端 `recordMcpAudit` 比照），操作紀錄頁人話字典已補齊。
- 單元測試：`databaseAcl.test.ts` 逐格驗權限矩陣。

### 2. 工作台（前端 `/databases`）

- 頂欄使用者選單「工作」區新增「資料庫」入口；頁面左欄按四層範圍列庫、右欄格線編輯（雙擊列即改、頂列直接新增、關鍵字搜尋）。
- 欄位驗證前後端共用 `shared/databaseFields.ts`（零漂移）：型別、必填、單選白名單、網址前綴、日期格式。

### 3. AI 代理系統

- **外部代理（MCP）**：新增三工具 `list_databases`（列庫＋欄位定義）、`query_database`（關鍵字查列）、`add_database_row`（寫一列，伺服器驗證型別）。金鑰擁有者是誰、權限就是誰的——與生成工具同一套 per-user 守衛。
- **站內團隊助手**（`teamAssistant.ask`）：組可見的組／團隊／全站資料庫（前 5 庫 × 各 12 列）自動注入上下文，組長可以直接問「器材借用表裡攝影機借給誰了」。個人庫刻意不進共享上下文。
- **AI 代理（agentRuns）**：v1 未把「寫資料庫」納入代理步驟型別；代理要讀寫資料庫時走 MCP 介面即可。若日後把它做成代理步驟，重用 `databaseAcl`＋`validateRowData` 兩個函式就是全部的接入成本。

## 三、往「大型組織」的擴展路線

現在的設計已為放大預留了位置，依序打開即可：

1. **量級**：`data_rows` 有 `(table_id, created_at)` 索引＋單庫 2 萬列保險絲；超過時（a）調高保險絲並在 `data.data` 上建 GIN 索引供 jsonb 查詢、（b）列表已是 offset 分頁、關鍵字走 SQL 而非撈全表。
2. **組織層**：目前「全站」＝單一組織。要多組織（多基金會共用一套系統）時，加 `organizations` 表、`teams.orgId`、`scope: "org"`——ACL 只多一個 case，資料表不動。
3. **RLS 第二道防線**：README 路線圖既有項目。應用層守衛已把 `groupId/teamId/ownerId` 正規化存欄位（不埋在 jsonb），未來直接對 `data_tables`／`data_rows` 上 Postgres RLS policy。
4. **欄位進階型**（關聯到另一庫的列、多選、附件）：`fields` 是 jsonb，加型別＝改 `shared/databaseFields.ts` 一處驗證＋前端一個輸入元件，無遷移。
5. **匯入匯出**：列資料是規整 jsonb，CSV 匯出／匯入是純 router 工作；「資料下載」頁可直接掛。

|---|---|
| `server/db/schema.ts` → `dataTables`, `dataRows` | 資料表（新表，pushSchema 安全） |

| `server/services/databaseAcl.ts`（＋test） | 權限矩陣單一真相＋可見庫查詢 |
| `server/routers/databases.ts` | tRPC：庫 CRUD＋列 CRUD |

| `server/routers/teamAssistant.ts` | 團隊助手上下文注入 |
| `client/src/pages/DatabasesPage.tsx`＋`App.tsx` | 工作台頁面與入口 |
| `shared/auditWording.ts` | 審計人話字典（新端點） |
