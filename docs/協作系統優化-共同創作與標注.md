## 一句話結論

**不要重做任何東西**：鏡像跟隨的演算法、版本投影、留言引用、advisory lock 註冊表、生成冪等鍵都已經寫得很好；真正缺的是五件小東西——**圖上的一個座標**（`messages` 加 5 欄）、**站內的一個收件匣**（`notifications` 一張表）、**分鏡的一個版本號**（`scenes.rev` 一欄＋一支收斂寫入的服務函式）、**invalidate 的一個 scope 欄位**，以及**鏡像期間的一行 CSS 覆蓋**。這五件加起來大約三期、六到八週的單人工作量，第一期兩天就有感。

### A-1 資料模型：`messages` 加五欄＋一個 kind，不開新表

**為什麼不開新表**：`server/db/schema/agents.ts:171-203` 已經有 `project_tasks`（含 `assigneeId`／`status`／`sourceMessageId`），`schedule_items` 也已經是「留言轉待辦」的落點（`MessagePanel.tsx:738-742`）。再開一張帶 assignee + open/resolved 的 `scene_notes`，半年後「這個專案還有幾件事沒做」會有**三個互相矛盾的答案**。而長在 `messages` 上，ACL 直接繼承既有的 `loadProject` + `requireGroup`（`server/routers/messages.ts:214`），連權限都不用重新設計。

```sql
-- drizzle/0040_scene_annotations.sql
ALTER TABLE messages
  ADD COLUMN anchor_asset_id uuid,      -- 標注釘在哪一版的成品；null＝一般引用留言
  ADD COLUMN ax real,                   -- 0..1，相對「媒體內容框」而非元素框（見 A-3）
  ADD COLUMN ay real,
  ADD COLUMN t_ms integer,              -- 影片/音訊時間碼；null＝靜態圖
  ADD COLUMN resolved_at timestamp,
  ADD COLUMN resolved_by uuid;

-- 標注型留言以 kind='annotation' 區分（messages.kind 已是自由 text，預設 'text'，
-- 既有值有 text/voice/assistant）。既有的「討論」留言全部維持 kind='text'，
-- 所以未解決計數 **零誤算、零 backfill**。
CREATE INDEX messages_ref_idx ON messages (ref_type, ref_id, created_at)
  WHERE ref_id IS NOT NULL;
CREATE INDEX messages_open_annotation_idx ON messages (project_id, ref_id)
  WHERE kind = 'annotation' AND resolved_at IS NULL;
```

**語意規則（寫進 schema 註解）**：
- `anchor_asset_id` 存的是 **assetId，絕不存「v2」這種版次字串**。`shared/sceneVersions.ts:202-213` 的版次 index 是每次查詢即時算的、不落庫，任何人指派一張舊素材就會讓既有版次整批位移。這是三份提案唯一一致同意、我也逐行驗證過的判斷。
- `ax/ay` 是 0..1，沿用 `server/services/realtime.ts:337` 的 `clamp01` 慣例。
- `resolved_at`／`resolved_by` 是**全組共用的單一狀態**，3-8 人單組不需要 per-user ack。

### A-3 座標怎麼算（這是唯一會整批做錯的地方）

`client/src/styles.css:5395-5400` 的舞台是：

```css
.scene-studio__media { width: 100%; max-height: 62dvh; object-fit: contain; ... }
```
（≤900px 再降成 `max-height: 40dvh`，`styles.css:5492`）

**`object-fit: contain` 表示元素框裡有 letterbox 留白，元素 rect ≠ 畫面框。** 直接用 `(e.clientX - rect.left) / rect.width` 算，只要素材長寬比與元素框長寬比不同（16:9 素材配手機直式版面幾乎必然），**所有標注會系統性偏移，而且畫面上沒有任何症狀**。

修法——一支純函式，配單元測試：

```ts
// shared/mediaPoint.ts（新檔）
export function mediaPointFromEvent(
  box: { left:number; top:number; width:number; height:number },  // 元素 rect
  intrinsic: { w:number; h:number },                               // naturalWidth/Height 或 videoWidth/Height
  ev: { clientX:number; clientY:number },
): { ax:number; ay:number } | null {
  if (!intrinsic.w || !intrinsic.h || !box.width || !box.height) return null; // 尚未載入＝不收點
  const scale = Math.min(box.width / intrinsic.w, box.height / intrinsic.h);  // contain
  const cw = intrinsic.w * scale, ch = intrinsic.h * scale;
  const ox = box.left + (box.width - cw) / 2, oy = box.top + (box.height - ch) / 2;
  const ax = (ev.clientX - ox) / cw, ay = (ev.clientY - oy) / ch;
  if (ax < 0 || ax > 1 || ay < 0 || ay > 1) return null;  // 點在 letterbox 上＝忽略
  return { ax, ay };
}
```
反向（畫圓點）用同一支函式的 inverse。**`assets` 表沒有 width/height 欄（`server/db/schema/generation.ts:107-147` 只有 `meta` jsonb），所以這件事只能在 client 算，一次做錯就是所有標注永久偏掉——因此它必須是 shared 純函式＋測試，不能寫在元件裡。**

### B-2 `notify()` 的順序契約（這是整份設計最重要的一行）

```ts
// server/services/notify.ts（新）
export async function notify(input: NotifyInput): Promise<void> {
  // 1. 先 await 落列（保底通道；推播整條掛掉也不影響這一步）
  const rows = await db.insert(schema.notifications).values(...).onConflictDoNothing().returning();
  // 2. 才推播，而且 **逐人** 推——不能用彙總回傳值判斷送達
  for (const row of rows) {
    void pushToUsers([row.userId], { title: row.title, body: row.body, url: row.url, tag: ... })
      .then((r) => db.update(schema.notifications)
        .set({ pushState: r.error ? "error" : r.attempted === 0 ? "no_device" : r.delivered === 0 ? "failed" : "delivered" })
        .where(eq(schema.notifications.id, row.id)));
  }
}
```

**為什麼一定要逐人推**：`server/services/webPush.ts:73` 的簽名是 `pushToUsers(userIds[], …) → { attempted: subs.length, delivered }`——`attempted` 是**跨所有收件人的訂閱列數**，不是人數。一則 @ 了三個人、只有組長有裝置時回傳 `{attempted:1, delivered:1}`，用彙總值回寫會把另外兩人記成 `delivered`。這條在評審裡被點出來，我開檔確認為真（`webPush.ts:75, 81, 110`）。

**額外要改一行**：`webPush.ts:111-115` 的外層 catch（DB 讀不到／VAPID 取不到）也回 `{0,0}`，與「這個人沒有任何裝置」完全無法區分。**加一個 optional 的 `error?: true` 欄位**（additive，另外 9 個呼叫端忽略多餘欄位，零破壞），讓系統故障不會被記成 `no_device`。

### C-2 校正時機：拆兩套壽命，但不要一直修

現在 `CURSOR_TTL_MS = 4000`（`realtime.tsx:46`）一到，`:492` 把 cursor 從 map 刪掉，迴圈 `:758-760` 就空轉。但**單純保留 lastCursor 也不對**：`realtime.tsx:760` 有 `if (cur.ts === lastCursorTs) return;` 的守衛，不移除它保留了也不會重新校正；移除它就變成每一幀都在跟使用者的手動捲動打架。

正確做法是**把「跟隨目標」與「重新校正的觸發」分開**：

- `presenceRef`：每人最後一則 cursor payload，**不過期**（只在對方離房時清），跟隨迴圈讀它。
- 游標圖示仍照 4 秒 TTL 消失（`CursorOverlay` 用 `cursors`，行為不變）。
- **重新校正只在三種事件觸發**：(1) 收到新封包（`cur.ts` 變了）；(2) 錨點元素的 `ResizeObserver` 回報尺寸變動（content-visibility 展開、骨架屏→真內容）；(3) 收到帶 `scope` 的 invalidate。**不做每幀輪詢**——那會讓跟隨者永遠捲不動。

### C-3 協定擴充（保守版：只加四個 optional 欄位）

`client/src/realtime.tsx` 與 `server/services/realtime.ts` 檔頭都註明協定要兩邊一起改。新欄位全 optional，新舊端可混跑（舊端看到多餘欄位就忽略，退回目前行為）。

```jsonc

{ "type":"cursor", "x":…, "y":…, "anchor":…, "ax":…, "ay":…, "vy":…, "vx":…, "ci":…,
  "conn": "a1b2c3d4",                 // 分頁 id，≤8 字元 [a-z0-9]
  "st": 1234, "sh": 9876,             // 根捲動 scrollTop/scrollHeight（退路用）
  "view": { "tab":"story", "mode":"direct", "filter":"missing", "exp":"1" },  // 全 ASCII，各值 ≤16
  "modal": "scene-studio:<uuid>" }    // ≤48，/^[a-z-]+:[0-9a-f-]{36}$/
```

**刻意不加的**：`sel`（選取範圍）、`t`（播放時間碼）、`vw/vh`（視窗尺寸）。理由見〈明確不做〉。

伺服器（`server/services/realtime.ts:322-347`）逐欄驗證後才轉發，沿用既有「不信任 client」原則。**訊息長度上限維持 2048 字元**（`realtime.ts:325`）——新欄位全是 ASCII，加起來 200 字元內。同時把 `maxPayload` 從 4096 提到 16384 bytes（`realtime.ts:405`）當保險：那是 **bytes**，而 zone 名稱是中文（「世界觀／生成台／素材庫／分鏡／留言」），一則 3000 字元的訊息就超過 6000 bytes，ws 會以 1009 **直接關掉整條連線**，使用者體感是「協作隨機斷線」。這兩個數字必須一起看。

**兩則新訊息**（伺服器 `ws.on("message")` 現在只認 cursor/focus/invalidate，`realtime.ts:321-367`）：


# 四道難題怎麼解

## (a) 標注跟版本：v2 改成 v3，標注去哪裡

**存 `anchor_asset_id`（assetId），絕不存「v2」這種版次字串。** `shared/sceneVersions.ts:202-213` 的版次 index 是每次查詢即時算的、不落庫；外部素材照 `asset.createdAt` 插進排序（`sceneVersions.ts:191, 204-209`），所以**任何人指派一張舊素材就會讓既有版次整批位移**。存版次號一定漂掉。

**釘死，不自動浮動。** 標注永遠屬於它被畫下的那一版。舞台顯示現用版時：
- `anchor_asset_id === scenes.assetId` → 直接畫在圖上；
- 不等於 → 收成一條「來自第 2 版的 2 則未解決標注（點看）」橫幅，點了把舞台切回第 2 版並疊上標注（`stageVersion` 機制已存在，`SceneStudio.tsx:202`）。

換版換構圖時自動浮動**一定會標錯地方**，比不指還糟。取而代之給兩個明確動作：
- **「這版已改好」** → `resolve`，圓點轉空心、分鏡格未解決數 -1、notify 原作者；
- **「還是要改」** → 在新版上點一次 → 建新列（`anchor_asset_id` = 新版、新 ax/ay、body 沿用可編輯），舊列同時 resolve。

**要不要沿用座標？** 加一欄 `generations.source_asset_id`（`server/db/schema/generation.ts:8-58` 現在只有 `sourceUrl`，是給供應商的短效簽名網址；`scenes.refine` 明明已經算出 `source.id`（`scenes.ts:847-853`）卻丟掉了）。有了它就分得出「v3 是從 v2 修出來的」還是「重畫的」：前者橫幅可以順便在同座標畫虛線空心圓點當參考；後者不畫。**這是加分項，不是前提**——既有生成全是 null，UI 文案要寫成「無法判斷與上一版的關係」，不能寫死「這是重畫的」。

> **老實說**：這個模型只解到「一版一版往下傳」的深度一層。兩輪 refine 之後，第一版的標注仍在，但要人手動一路搬。對 3-8 人一支片十幾鏡的規模，這是對的取捨；再往上做就要引入 lineage 圖，成本不成比例。

## (b) 提醒不遺失

**三層，順序是關鍵。**

1. **先落庫，再推播。** `notify()` 第一步是 `await insert notifications`，第二步才 `void pushToUsers`。推播降級成**加速通道**，站內收件匣是**真相**。現在 `messages.ts:242` 是 fire-and-forget，`webPush.ts:105-107` 失敗只 warn 且沒有任何佇列會再試——推播丟了就永遠沒了。
2. **逐人推、回寫 `push_state`。** 見 B-2：不能用彙總回傳值，還要能區分「沒裝置」與「系統故障」。這是第一次讓「某則 @ 從來沒送達」在系統裡看得出來。
3. **已讀是 per-row 的 `read_at`，與「已解決」的 `resolved_at` 是兩個欄位、兩個生命週期。** 這一點必須寫死：一則純 @ 留言（沒有 refId、沒有 ax/ay，例如快速短語）永遠不會被 resolve；如果收件匣拿 `resolved_at is null` 當篩選條件，鈴鐺就**永遠不會歸零**。同理，`resolve` 用 `requireGroup` 是對的（任何組員能收掉一件事），但它**不能同時擔任「已讀」**——否則任何人都能清掉別人的收件匣。

**做完之後**：沒訂閱推播的人（除組長外幾乎全部）一登入就在鈴鐺上看得到；推播只影響「多快知道」，不影響「會不會知道」。

## (c) 併發覆蓋

分成三種撞車，**三種不同的解**，刻意不用同一把錘子。

**c-1 文字欄位：`rev` 整數樂觀鎖 ＋ 單一寫入漏斗**

```sql
-- drizzle/0042_scene_rev.sql
ALTER TABLE scenes
  ADD COLUMN rev integer NOT NULL DEFAULT 0,
  ADD COLUMN updated_at timestamp NOT NULL DEFAULT now(),
  ADD COLUMN updated_by uuid;
```

**用 `rev` 整數而不是 `updatedAt` 時間戳做比較鍵**：`DEFAULT now()` 回填是 Postgres 微秒精度，drizzle pg `timestamp` 預設 `mode:'date'`，經 tRPC JSON 往返只剩毫秒——`eq(scenes.updatedAt, expected)` 對**每一列既有分鏡永遠不相等**，遷移後第一次存檔一律 CONFLICT。整數沒有這個問題。（`updated_at`／`updated_by` 仍然要加，那是給「誰改的、什麼時候」用的，不參與比較。）

**只加欄位不夠——現在有八個地方在寫 scenes**（`scenes.ts:442/473/634/710/748`、`generationCore.ts:1012`、`assistant.ts:902/907`、`mcpWriteExpansion.ts:484/529）。只在 `scenes.update` 帶 `rev+1`，AI 助手改過的分鏡樂觀鎖會**靜默放行**，而 `updated_by` 從此變成會說謊的欄位。

所以新增 `server/services/sceneWrite.ts`，**所有內容欄位寫入唯一入口**：
```ts
export async function updateSceneFields(tx, sceneId, patch, actorId, expectedRev?)
// - 一律 set rev = rev + 1, updated_at = now(), updated_by = actorId
// - expectedRev 有帶時 where 補 eq(scenes.rev, expectedRev)，0 列 → CONFLICT
// - 內建欄位上限（用 shared/storyboardScript.ts 的 SCRIPT_* 常數）與素材 kind 守門
```
順手修掉兩條旁路的不一致：`mcpWriteExpansion.ts:456/481` 把 voiceover **靜默截到 500 字**（`scenes.ts:614` 的上限是 2000）、`mcpWriteExpansion.ts:524-533` 的 `set_scene_visual` **完全沒有 kind 檢查**（`scenes.ts:434-439` 特地擋住，註解還寫「audio 模型會把音訊寫進 visual 槽造成破圖」）。截斷改成明確報錯。

**執行邊界**：`scripts/check-import-boundaries.mjs` 已經是 repo 既有的守門機制，加一條規則——`update(schema.scenes)` 只准出現在 `sceneWrite.ts`（orderIndex／deletedAt 那幾支走既有的 `lockSceneOrder` 路徑，明列白名單）。沒有這條，半年後又會長出第九個寫入點。

**`expectedRev` 是 optional，不帶時不做 CAS**——上線瞬間手上開著舊頁面的人不會全員 CONFLICT。這句話要寫進 PR 描述，不能被後續「順手改成 required」。

前端衝突處理零成本：`SceneStudio.tsx:105-107` 的 `promptDraft` 是「null＝跟隨伺服器」，成功時才 `setPromptDraft(null)`（`:146`）。**衝突時不要設 null**，使用者的字自然留在輸入框，旁邊顯示「他的版本」讓人比對。同批修 `SceneStudio.tsx:342-346` 的「已儲存 ✓」常駐（改 2 秒 timeout）。

**c-2 重複扣點：用 partial unique index，不用 advisory lock**

三份提案都想加一個 lock class 8 把「查在途 → 建生成 → 扣點」包進同一個交易。**這條路走不通，我開檔確認過**：
- `server/services/points.ts:289` 的 `reserveQuota` **自己開 `db.transaction`**，用的是 `db` 不是傳入的 tx —— 包在外層交易裡，扣點是另一條連線的獨立交易，外層 rollback 時點數不會退，直接製造「生成列沒了、點卻扣了」的新漏點路徑；
- `points.ts:272-274` 註解明文警告「交易內不可再向連線池借第二條連線，否則交易已佔一條連線＋持有序列化鎖時再借連線，**併發滿池會整池死鎖（需重啟才復原）**」；`points.ts:286` 的 `falCeilingReason` 還是外部 API；
- `generationCore.ts:830-840` 在 reserveQuota 失敗時用 `db.delete`（非 tx）刪掉剛建的 queued 列，外層若在交易中會等自己未 commit 的 insert；
- `generationCore.ts:855-857` 的 `falSubmit` 是外部 HTTP，包進持鎖交易＝3-8 人同按就吃光連線池；
- `server/services/locks.ts:9` 白紙黑字寫著「approvals 從不在持有此鎖時呼叫 reserveQuota，故無交叉取得的死鎖面」——**提案要做的正是那件被明文避開的事。**

改用 DB 約束，成本是十分之一：

```sql
-- drizzle/0042_scene_rev.sql（同一支）
-- 上線前先把既有重複列收尾（同一 scene 多筆在途）：
UPDATE generations SET status='failed', error='系統清理：同格重複在途'
 WHERE id IN (SELECT id FROM (SELECT id, row_number() OVER (
        PARTITION BY scene_id, coalesce(scene_role,'visual') ORDER BY created_at) rn
      FROM generations WHERE scene_id IS NOT NULL
        AND status IN ('queued','running','awaiting_approval')) x WHERE rn > 1);

CREATE UNIQUE INDEX generations_scene_visual_uq ON generations (scene_id)
  WHERE scene_id IS NOT NULL AND status IN ('queued','running','awaiting_approval')
    AND (scene_role IS NULL OR scene_role = 'visual');
CREATE UNIQUE INDEX generations_scene_narration_uq ON generations (scene_id)
  WHERE scene_id IS NOT NULL AND status IN ('queued','running','awaiting_approval') AND scene_role = 'narration';
CREATE UNIQUE INDEX generations_scene_ambience_uq ON generations (scene_id)
  WHERE scene_id IS NOT NULL AND status IN ('queued','running','awaiting_approval') AND scene_role = 'ambience';
```

這個形狀 repo 已經在用（`generation.ts:66-72` 的 `activeIdx` 就是 `.where(sql\`status in ('queued','running')\`)`），所以 drizzle 表達得出來。插入端的 catch **已經存在**（`generationCore.ts:734-739`、`:802-807` 的 `isUniqueViolation`），只要多一個分支：依 `(err as {constraint?:string}).constraint` 判斷是 scene 去重索引 → 丟人話 CONFLICT「這一格正在生成或待核准中」。`assertNoPendingVisual`（`scenes.ts:95-107`）保留當快速失敗的前置檢查，但**真正的保證在 DB**。順帶把 `scenes.ts:918, 968` 漏掉的 `"awaiting_approval"` 補上。

> **要先驗證的一件事**：`npm run db:check` 的漂移閘（`scripts/db/check.ts:53-56`）會用 drizzle-kit 回讀實際 schema 比對。partial unique index 的 predicate 正規化（`scene_role IS NULL OR scene_role = 'visual'`）**有可能**被 Postgres 回讀成不同字串而被判為 drift。這是整份計畫裡最可能卡住的一步，第一天就要跑一次確認。若真的卡，退路是用 `coalesce(scene_role,'visual')` 的表達式索引，或最後才退回 `assertNoPendingVisual` + 應用層檢查。

**c-3 背景回填推翻人工決定：CAS，用 `IS NOT DISTINCT FROM`**

`generationCore.ts:1010-1015` 現在只檢查沒被軟刪。加條件時**不能寫 `eq(scenes.assetId, expected)`**——第一次出圖時 `expected` 是 null，SQL 的 `asset_id = NULL` 恆為 unknown，0 列更新，「按下生成 → 圖回填分鏡格」這條**最核心的流程會整批靜默失效**。（這是三份提案裡兩份都犯的同一個錯，我逐條驗過 `projects.ts:176` 的 `assetId` 確實可為 null。）

正確寫法一個 SQL 運算子就解決：

```sql
WHERE id = :sceneId AND deleted_at IS NULL
  AND <slot> IS NOT DISTINCT FROM :expected
```

`expected` 存在哪裡：`generations` 加一欄 `scene_pointer_at_submit jsonb`。**用 jsonb 而不是 uuid**，因為要區分三種狀態：`NULL`＝舊資料／非分鏡路徑（**不做 CAS，維持現行行為**）、`{"v":null}`＝送出時該槽是空的、`{"v":"<uuid>"}`＝送出時指向某版。只在 `submitGenerationCore` 的分鏡綁定路徑（已經收 `sceneId`／`sceneRole`，`generationCore.ts:715-716`）多寫一個 optional 欄位，不改核心簽名的其餘部分。

CAS 不中時：**不覆蓋**，成品仍然進 `assets` 與版本清單（什麼都沒丟），改發一則 `kind='generation_done'` 的通知「新版本已完成，要切過去嗎」＋一則帶 scope 的 invalidate。

**c-4 `applyScript`：加基準指紋，不改對應規則**

我實際讀了 `shared/storyboardScript.ts:243-270`：`resolveScriptTargets` 是「標題鏡次優先、否則依序」，檔內註解明寫這是刻意的（匯出只留「## 1. A」與「## 3. C」時，C 仍對到第 3 鏡）。**把它改成 sceneId 對應會拿掉「在文字裡通讀重寫」的既有語意，而且既有專案在重新匯出腳本前那份舊文字沒有標記，過渡期每一次寫回都走退化路徑——原本的 bug 原封不動。**

所以不動對應規則，只加一道基準檢查：

這一條就把「乙刪一格 → 甲寫回把 B 的內容蓋到 C 上」整類問題堵死，而且**不動任何既有語意**。同批：

# 明確不做

1. **不做分工表／任務指派／assignee 欄／看板。** 3-8 人單組、幾乎都是組長本人在做，「這一格歸誰」不是問題；問題是「這一格哪裡要改、改完了沒」。而且 `server/db/schema/agents.ts:171-203` 的 `project_tasks` 已經有 `assigneeId`／`status`／`sourceMessageId`，`schedule_items` 也已經是「留言轉待辦」的落點——再加第三個帶 assignee 的東西，半年後「還有幾件事沒做」會有三個答案。
2. **不復活 `approvals` 表**（`server/db/schema/projects.ts:203-217`，檔頭註解自承「沒有任何應用程式碼讀寫它」），**不補 `scenes.status` 的寫入入口**。`needs_work` 直接用「這一格有未解決標注」投影（`SceneRow` 的未解決數 pill），多一套狀態機就多一份要對帳的真相。
3. **不做 CRDT／OT 逐字元共編（Yjs/Automerge）。** `rev` 樂觀鎖＋看得懂的 CONFLICT 提示就夠；CRDT 要動 scenes 全部欄位的儲存格式、離線合併與一整套新的持久化層，換到的是這個規模用不到的併發度。
4. **不追求像素級 1:1 鏡像。** `docs/wiki/協作與鏡像跟隨.md:29` 已經自承不做。**不加 `vw/vh/dpr` 進協定、不做手機與桌機版面的座標換算。** 目標是「捲到同一格」而非「同一個像素」。
5. **不把 `sel`（選取範圍）與 `t`（播放時間碼）加進 presence 協定。** 現有的 `ci` 已能表達 input/textarea 的游標位置；非表單內容的選取範圍要怎麼序列化、怎麼在對方 DOM 上還原，沒有便宜的答案。播放時間碼存在標注的 `t_ms` 裡就夠，一起看粗剪不是這一批的目標。
6. **不開 email 後備、不做通知偏好矩陣、不做推播重試佇列與死信。** 站內鈴鐺已經把送達率從「只有組長」拉到「所有人一登入就看得到」；再加通道與偏好只會讓 `notify()` 變複雜，而且會讓「不遺失」這個承諾多出一堆例外。
7. **不做標注自動浮動、不做 AI 自動判斷「這一版是不是改好了」。** 前者換構圖時一定標錯地方；後者會讓人不敢相信那個未解決數字。這是刻意的取捨，不是還沒做。
8. **不把協作鋪到全站。** `ChatPage`／`SharedProjectPage`／`WorkflowsPage`／`AnimationStudioPage`／`WhiteboardCanvas`（`client/src/features/animation-studio/WhiteboardCanvas.tsx:258, 374` 有自己的 pointermove 但與 realtime 毫無關聯）一個都不碰。共同創作的密度集中在專案頁的分鏡上，鋪開只會讓每個地方都半吊子。
9. **不新開 `scene_events` 稽核軌跡表。** 標注本身就是可查詢的軌跡（誰提出、釘在哪一版、誰解決、何時），配上 `scenes.updated_by` 已足以回答「這一格為什麼變成這樣」。改 `audit.ts:81` 讓 groupId 填得到就好。
