# SLO、告警與事故應變

> 狀態：這是正式上線的**驗收門檻與操作契約**，不是目前線上環境已達成的證明。
> 上線負責人必須把 Zeabur/PostgreSQL/外部供應商的監控、通知與備份證據連回此文件，
> 並完成一次還原演練後，才能把成熟度標記為「正式營運」。

## 服務目標

| 指標 | 目標 | 量測邊界 |
|---|---:|---|
| 月可用率 | ≥ 99.9% | 外部每分鐘探測 `/api/health` 與 `/api/ready`；排除預先公告的維護窗 |
| 互動 API 延遲 | p95 < 800 ms、p99 < 2 s | 不含媒體生成、AI 問答、匯出等非同步工作 |
| 一般 API 錯誤率 | 5 分鐘窗 < 1% | HTTP 5xx；4xx 不計入服務錯誤 |
| 背景工作成功率 | 24 小時 ≥ 99% | generation/workflow/agent/export 的終局狀態，排除使用者取消 |
| PostgreSQL 備份 RPO | ≤ 15 分鐘 | 需平台 PITR 或等效 WAL 備份證據 |
| PostgreSQL 還原 RTO | ≤ 60 分鐘 | 以隔離環境的實際還原演練計時 |
| 素材 Volume RPO/RTO | ≤ 24 小時 / ≤ 4 小時 | DB 與 Volume 必須成對備份、成對還原 |

若目前方案無法提供 PostgreSQL PITR，必須把實際 RPO 改成可證明的數值，不能沿用上表。

## 必要探測與告警

- Liveness：`GET /api/health`。連續 3 次失敗才重啟，避免單次網路抖動造成重啟風暴。
- Readiness：`GET /api/ready`。任一 DB、啟動初始化、持久儲存或必要 runner 檢查失敗即停止接流量。
- Migration：release job 的 `db:migrate`/`db:check` 非零即阻止部署；Web replica 不執行 DDL。
- 錯誤率：5 分鐘 5xx > 1% 警告、> 5% 緊急；依 `X-Request-Id` 串接集中式日誌。
- 延遲：互動 API p95 > 800 ms 持續 10 分鐘警告；同時觀察 DB pool 等待與慢查詢。
- 背景工作：queued/running 最老工作超過其陳屍門檻、同類失敗率 > 5%、退款失敗均需告警。
- 容量：DB/Volume 70% 警告、85% 緊急；連線池 80% 持續 5 分鐘警告。
- 供應商：Fal/NVIDIA/Google 以不花費或低成本 canary 驗證認證與契約；不得只看本服務 200。

告警通知需至少有一個主要與一個備援接收者，並每季做一次測試告警。

## 事故等級

| 等級 | 例子 | 首次回應 | 更新頻率 |
|---|---|---:|---:|
| SEV-1 | 資料外洩、資料毀損、全站不可用、錯誤扣點大量發生 | 15 分鐘 | 每 30 分鐘 |
| SEV-2 | 核心生成/協作流程大面積失敗、部分租戶無法使用 | 30 分鐘 | 每 60 分鐘 |
| SEV-3 | 有替代路徑的局部功能或效能退化 | 1 個工作日 | 每工作日 |

任何人發現疑似資料外洩都先按 SEV-1 處理；證據確認前不可在公開頻道貼 token、cookie、
完整請求 body、私人訊息或使用者資料。

## 標準應變流程

1. **確認與止血**：記錄 UTC/台北時間、受影響功能、build SHA、request ID；必要時停用單一
   provider/runner 或把服務切成唯讀，避免資料繼續擴大。
2. **保留證據**：保存集中式 log、部署事件、DB 指標與 migration ledger；不要先清 log 或手動改 ledger。
3. **復原**：優先回滾至仍相容目前 schema 的映像；資料錯誤依 migration runbook 走 forward-fix
   或成對還原 DB＋Volume。
4. **驗證**：跑 `/api/ready`、核心 smoke、受影響 E2E，確認背景佇列與點數帳本已收斂。
5. **溝通**：只發布已確認的影響、暫時措施與下次更新時間，不猜根因。
6. **事後檢討**：5 個工作日內完成時間線、根因、為何既有防線沒攔住、永久修復、負責人與期限。

## 備份還原演練

至少每季一次，且每次破壞性 migration 前額外執行：

1. 取得同一時間邊界的 PostgreSQL 備份與 `/data` Volume 備份。
2. 還原到**新的隔離 DB 與 Volume**，不可覆蓋正式環境。
3. 使用與正式相同映像執行 `npm run db:check`，啟動後跑 ready/selftest 與核心 E2E。
4. 隨機抽查至少 10 個素材的 DB reference 與檔案雜湊，並驗證登入、權限、點數帳本。
5. 記錄開始/完成時間、備份時間點、RPO/RTO、失敗步驟與證據連結。

沒有最近一次成功演練的證據，就不得宣稱已達上表 RPO/RTO。

## 發布與回滾停止條件

遇到以下任一情況立即停止發布：

- migration dry-run/ledger/hash/drift 驗證不通過；
- 備份不存在、無法讀取，或沒有可操作的還原路徑；
- 新舊應用不能同時相容 expand 階段 schema；
- 5xx、p95、DB lock/pool 或背景失敗率超過基線兩倍；
- provider smoke、權限隔離、批次寫入冪等或強制改密碼流程失敗。

回滾應用不等於回滾資料庫。已提交的 schema/data 變更一律依
[`資料庫遷移.md`](./資料庫遷移.md) 的 forward-fix/還原規則處理。
