# 組代理總指揮（Group Agent Commander）

> 適用範圍：`shared/groupAgent.ts`、`server/services/groupCommand.ts`、`groupCampaignCore.ts`、
> `groupCampaignRunner.ts`、`server/routers/teamAssistant.ts`、`drizzle/0018_group_agent_commander.sql`。
> 專案代理本身的契約與執行語義見〈AI 代理架構與維運〉，本文只寫「組這一層」多出來的東西。

## 為什麼要做

組代理（作業台的團隊分析卡）原本只有**唯讀分析＋提議派工**：它看得到全組出事，卻碰不了任何一份專案代理計畫。

- 看得到一份子計畫失敗——不能重跑。
- 看得到三份待核堵在那裡——不能核准、也不能撤。
- 看得到誰逾期——不能改期、不能改派。

結果是：**專案代理才是唯一會動手的角色，統管全組的組代理反而比它弱**。使用者在組層看到問題，還得自己一個個點進專案頁去做那些它明明已經診斷出來的事。

這一層補的就是這個落差：讓組代理**能下令**（L1／L2），並且**能在無人盯著時持續下令**（L3）。

同時要守住一條線——能力變大不代表守門變鬆。所有落地一律轉呼叫既有的專案核心（`planAgentCore`／`approveAgentCore`／`stopAgentCore`／`discardAgentCore`／`updateProjectTaskCore`），組這一層只多驗兩件自己的事：**這個人有沒有這個等級**、**目標物是不是這個組的**。專案 ACL、封存、額度、規劃節流、併發鎖，一個都不繞過。

## 三層能力

| 層 | 名稱 | 內容 | 落在哪 |
|---|---|---|---|
| L1 | 監督權 | 跨專案核准／停止／放棄／重新規劃子計畫 | `runGroupCommand`（`groupCommand.ts`） |
| L2 | 調度權 | 批次派工、指派／改期／改優先序既有人類任務 | 同上＋`teamAssistant.commandBatch` |
| L3 | 常駐總指揮 | 組代理有自己的多步計畫（campaign）＋事件軌跡＋背景執行器；派完工會自己盯著子計畫，失敗在授權內補救，超出授權就停下來等人 | `groupCampaignCore.ts`＋`groupCampaignRunner.ts` |

三層共用同一個入口：**從對話框按、從卡片按、組代理在 campaign 裡自己按，走的都是 `runGroupCommand`**。這不是潔癖——三個呼叫端若各自去戳 core，遲早會出現「從卡片按可以、從 campaign 跑就少一道檢查」這種只有攻擊者會發現的落差。

### 指令集（六種）

| 指令 | 做什麼 | 轉呼叫 | 最低等級 | 狀態前提 |
|---|---|---|---|---|
| `dispatch` | 在某專案建立一份待核子計畫 | `planAgentCore` | dispatch | 專案屬於本組、未封存、可編輯 |
| `approve_run` | 核准子計畫（**這一刻起才開始花點**） | `approveAgentCore` | supervise | `awaiting_approval` |
| `stop_run` | 停止執行中／等待中的子計畫 | `stopAgentCore` | supervise | `running`／`waiting` |
| `discard_run` | 放棄尚未核准的子計畫（不花點） | `discardAgentCore` | supervise | `awaiting_approval` |
| `retry_run` | 以同一目標重新規劃一份 | `planAgentCore` | supervise | `failed`／`stopped` |
| `assign_task` | 改派／改期／改優先序一件既有人類任務 | `updateProjectTaskCore` | supervise | 任務屬於本組 |

狀態前提由各 core 自己擋（`PRECONDITION_FAILED`），組這一層不複製一份會走樣的規則；`ask` 產生提議時另用同一張表先過濾，避免給使用者一顆按下去必失敗的按鈕。

目標物不屬於這個組一律回 **`NOT_FOUND`**（不是 `FORBIDDEN`）：借道別組的 id 是最省事的越權手法，而錯誤碼本身也不該洩漏「這個 id 存在」。

## 分級授權（四級）

落庫在 `group_members.agent_command_level`（nullable text）。純規則在 `shared/groupAgent.ts` 的
`resolveCommandLevel`／`canRunCommand`／`levelAtLeast`，前後端共用同一份。

| 等級 | 誰會是這一級 | 能做什麼 |
|---|---|---|
| `none` | 未授權的一般組員（預設） | 唯讀：`ask`、`agentOverview`、`groupInsights`、看 campaign 清單 |
| `dispatch` | 被開了派工權的組員 | ＋在本組專案派工（產生待核計畫，仍需核准才花點） |
| `supervise` | 被組長明確授權的組員 | ＋核准／停止／放棄／重新規劃子計畫、調整人員任務 |
| `command` | 組長、團隊管理員、開發者（**由角色決定，不看欄位**）；或被明確授權的組員 | ＋發起／核准／續跑 campaign（＝授權它在無人盯著時自動核准、自動花點） |

### 為什麼不是一個布林

舊的 `canDispatchAgent` 只回答一件事：「能不能生出一份待核計畫」。而「能不能替別人核准、讓它現在就開始花真金白銀的點」「能不能讓組代理在無人盯著時自己補救」是**完全不同量級**的授權。折在同一個布林裡，等於每次開派工權都把最貴的權限默默一起送出去。詳見 ADR-010。

### 相容與寫入規則

- 讀：`agent_command_level` 有明確值就用它；`null`（欄位剛上線、從沒設過）退回舊布林 `canDispatchAgent`（`true` → `dispatch`，否則 `none`）。既有授權不會在 migration 當下無聲失效。
- 寫：`quota.setMemberCommandLevel`（新，四級）與 `quota.setMemberDispatch`（舊，開關）**都一律兩欄一起寫**。只寫一欄的話，另一條讀取路徑會看到相反的答案。
- 舊開關的兩條規則刻意不對稱（`levelFromDispatchToggle`）：**打開時不降級**（已是 supervise 的人按「開」不會被降回 dispatch——使用者按的是「開」，權限卻變小，沒有人會預期）；**關掉時一律寫 `none`**（收權必須是真的收權，寧可多收也不能假收）。
- 守門與個人預算同一把尺：組長可調別的組員，**調自己需團隊管理員以上**。supervise 以上能直接開始花點，讓被授權者自己往上調等於把提權的鑰匙交到他手上。

## Campaign：步驟種類與執行模型

### 五種步驟（只有這五種）

| 種類 | 做什麼 |
|---|---|
| `dispatch` | 在某專案建立子計畫 |
| `watch` | 盯著某個 `dispatch` 步驟產生的子計畫：核准 → 等終局 → 失敗時在授權內重新規劃 |
| `assign_task` | 指派／改期一件既有人類任務 |
| `wait_for_human` | 組級人工關卡：整份計畫轉 `waiting`，要有人按繼續 |
| `report` | 產出一段結論（不動任何資料） |

刻意比專案代理少很多：組代理**不生圖、不配音、不改分鏡、不寫資料庫**，那些是專案代理的工作。規劃提示詞把這句寫死在第一段——沒有這句，LLM 幾乎必然排出 `create_scene`／`generate` 這種它根本沒有的步驟，然後整份計畫在 `resolveCampaignPlan` 被丟成空計畫，使用者只看到「規劃失敗」卻不知道為什麼。

規劃器輸出的是**代號草稿**（`p1`／`t1`／`u1`），不吐 UUID；`resolveCampaignPlan`（純函式）是唯一的落地閘：代號幻覺、目標不足 5 字、`watch` 指不到任何 `dispatch`、依賴指向被丟掉的步驟、自我依賴、超過 12 步——各自對應一種「看起來合理、執行起來一定爆」的輸出，一律在落庫前就丟掉。`watch` 天然依賴它盯的那一步，LLM 漏寫也會補上（否則會在子計畫還沒建立時就開始盯）。

### 執行模型

背景執行器 `groupCampaignRunner`，每 **8 秒**一 tick，每輪最多撈 20 份 `running` 的 campaign。

1. **每 tick 每份計畫只推進一步。** 組級步驟每一步都可能觸發一次 LLM 規劃（`dispatch`）或一次核准（開始花錢）。一次跑完一整排等於把整個組的點數在四秒內送出去。
2. **`watch` 是輪詢不是阻塞。** 子計畫可能跑數十分鐘；執行器不會在那裡等，每輪回來看一眼。tick 內先掃所有 `running` 的 `watch`，沒有任何進展時才推進一個新步驟。
3. **超出授權就停下來等人**，不是「先做了再說」，也不是「整份失敗」。一份因為估點多 10 點就整份失敗的計畫，使用者只能整份重排——那比停下來問一句糟得多。
4. **每輪重驗發起人。** 執行器用 `loadAuthState(run.userId)` 以**發起人的身分**下令（不是什麼超級帳號），所以發起人的專案 ACL 與額度照樣生效。發起人被停用或被移出組，整份計畫立刻停手並記 `campaign:authority-lost`。
5. **多副本只有一個 process 在推。** 走 `withRunnerAdvisoryLock('group-campaign:<id>')`——重複執行的代價是雙倍點數。
6. **依賴確定不會完成的支線標成 `skipped`**（`skipUnreachableSteps`，遞移閉包）。沒有這步，一個 `dispatch` 失敗會讓後面每一步永遠 `pending`，run 既不 done 也不 failed，變成每 tick 都被撈起來又什麼都不做的殭屍。

`watch` 每一輪的決策是純函式 `decideWatchAction`（`shared/groupAgent.ts`），順序有意義：

```text
子計畫 awaiting_approval → 放得進授權？ 放得進 → approve（核准成功才記帳）
                                        放不進 → hold（步驟轉 waiting，等人加授權）
子計畫 running / waiting  → wait（什麼都不做，下輪再看）
子計畫 done               → done
子計畫 failed             → 還有重試額度 → retry（重新規劃，產出的仍是待核，下一輪才核准）
                            沒有         → fail（理由寫清楚是「試過幾次」還是「本來就不重試」）
子計畫 stopped / discarded→ fail 且不重試（那是人做的決定，不該把人剛停掉的東西再開一次）
```

### 生命週期

```text
planCampaign ──▶ awaiting_approval ──approveCampaign──▶ running ──┬──▶ done / failed / stopped
                        │                                  ▲      │
                  discardCampaign                          │      └──▶ waiting ──resumeCampaign──┘
                        ▼                          （背景執行器每 8 秒推一步）   （可就地加授權）
                    discarded
```

- `planCampaign`／`approveCampaign`／`resumeCampaign` 三支共用同一道閘 `assertCampaignAuthority`（需 `CAMPAIGN_MIN_LEVEL` ＝ `command`），`approve`／`resume` 另需**發起人或組長以上**；`stopCampaign`／`discardCampaign` 只驗**發起人或組長以上**（不另看等級——收拾自己發起的東西不該再要一次授權，而且「停手」永遠不該比「開始」難）。
  - 為什麼 campaign 的門檻自成一個常數而不是塞進 `COMMAND_MIN_LEVEL`：那張表的鍵是「一道人按下去的指令」——按一次、花一次、有人看著；campaign 是「授權組代理在無人盯著時反覆下那些指令」。混用的後果不是多給一點權限，而是成員設定頁那段「可監督不會自動花錢」的說明在騙人。
  - `resume` 特別要求發起人或組長以上的理由：它是唯一會**調高** `budgetPoints` 的入口，而執行器是以**發起人**身分下令、扣發起人的額度。讓旁人拉高它，等於替發起人簽了一張他沒同意的授權書。
- `discardCampaign` 只吃 `awaiting_approval`（純標記、沒花任何點）；`stopCampaign` 只吃 `running`／`waiting`。
- 終局由 `resolveCampaignOutcome` 折：有 running／waiting／pending → 未結束；有 failed → failed；有 stopped → stopped；其餘（全 done，或 done＋skipped）→ done。**「有 skipped 就算失敗」是錯的**：使用者停掉一條支線後其餘正常完成，那份計畫是完成的。

## 點數授權的安全性質

每份 campaign 帶 `budgetPoints`（本次授權組代理可**自動核准**的點數上限）與 `spentPoints`（已自動核准掉的估點）。

- **預設 0 ＝ 不授權自動花點。** `withinCampaignBudget` 對 `budgetPoints <= 0` 一律回 false。預設不給、要人明確填，比預設給了再靠人記得關安全。
- **超出不是失敗，是停手等人。** 步驟轉 `waiting`、理由寫進 `step.error`，`resumeCampaign(addBudgetPoints)` 可就地加額度續跑。刻意**不提供「解除上限」選項**——那等於把好不容易加上的閘直接拆掉。
- **先核准成功才記帳。** 先加後核准的話，核准被併發鎖擋下會白白吃掉授權額度。
- **每輪重讀最新的 `budget/spent`**：同一份 campaign 的其他 `watch` 步驟可能剛核准過別的子計畫。
- **授權以「估點」計，不是實扣。** `estPoints` 是規劃時的估算，實際扣點以各步生成為準，各步另有 `reserveQuota` 硬守門。所以 `budgetPoints` 是**自動核准的閘**，不是帳本上限——真正的花費上限仍是使用者／組的額度。
- 授權只約束**組代理自己按的核准**。人自己去專案頁按核准不吃這個閘（那本來就是人的決定）。

## 組代理不會做什麼

寫在這裡是因為這幾件事最容易被誤會成「它應該會」：

- **不生圖、不配音、不做任何內容生成。** 它只會叫專案代理去做。
- **不改分鏡、不寫資料庫、不寫筆記或排程。** 組級步驟只有五種，沒有內容副作用。
- **不建立新的人類任務。** `assign_task` 只能調整**既有**任務的負責人／期限／優先序。
- **不建立專案。** 只能在既有、未封存的組內專案上派工。
- **停止 campaign 不會停已派出的子計畫。** 那些是各專案自己的計畫，可能已經花了點、跑到一半，替它們決定生死不是這裡該做的事。要停請對那份子計畫下 `stop_run`（清單上就有）。這一條寫進了 API 回傳訊息，免得使用者以為按了停止就什麼都不會再花錢。
- **不會用比發起人更大的權限做事。** 它借的是發起人的身分；發起人做不到的，它也做不到。
- **不重開人剛停掉的東西。** 子計畫被 `stopped`／`discarded` 時 `watch` 一律不重試。
- **不會自己解除自己的授權上限。**

## 維運

### 兩張新表（`drizzle/0018_group_agent_commander.sql`）

| 表 | 用途 | 關鍵欄位 |
|---|---|---|
| `group_agent_runs` | 組代理的 campaign | `group_id`、`user_id`（發起人＝下令身分）、`goal`、`summary`、`status`、`steps`（jsonb，執行器是唯一寫者）、`budget_points`、`spent_points`、`error` |
| `group_agent_events` | 組級事件軌跡 | `group_id`、`run_id`（campaign；L1／L2 從卡片下的指令為 **NULL**）、`project_id`、`child_run_id`、`step_id`、`event_key`、`event_type`、`actor_type`（`ai`／`human`／`system`）、`summary`、`data` |

另加 `group_members.agent_command_level`（nullable text；`null` 時退回舊布林）。

**為什麼不共用 `agent_events`**：那張表 `project_id` NOT NULL，而組代理最重要的幾件事——下令、超預算停手、跳過整條支線、發起人失去授權——**不屬於任何單一專案**。詳見 ADR-010。

索引：`(group_id,status,updated_at)`、`(status,updated_at)`（執行器撈 running 用）、`(run_id,event_key)` 唯一、`(group_id,created_at)`、`(run_id,created_at)`。

`(run_id,event_key)` 唯一鍵讓執行器崩潰重跑同一步時**重播為 no-op**；但 Postgres 的 NULL 彼此不相等，所以 `run_id IS NULL` 的卡片指令事件不受此去重約束（同一道指令下兩次會有兩筆——那本來就是兩件事）。

### 背景執行器

- 啟動在 `server/index.ts`：`startGroupCampaignRunner()`，log 為 `[groupAgent] 組代理總指揮執行器已啟動（每 8 秒推進一次）`。**看不到這行就代表沒有人在推 campaign。**
- 開機另跑一次 `sweepStaleCampaigns()`：把上一個 process 留下的「`running`／`waiting` 但一小時沒動」的計畫記一筆觀察事件，**不自動改狀態**——自動判死太容易誤殺（可能只是子計畫真的跑很久）。
- 執行中的計畫超過一小時沒進展也會記 `campaign:stale`。

### 怎麼看事件軌跡

- API：`teamAssistant.campaign({ runId })` 回 `{ run, events }`（最近 60 筆，該 campaign 範圍內）。
- **注意**：L1／L2 從卡片／對話框下的指令 `run_id` 是 NULL，目前**沒有 API 讀得到**，只能查表：

```sql
-- 某份 campaign 的完整軌跡
select created_at, event_type, step_id, child_run_id, summary
from group_agent_events where run_id = '<campaign id>' order by created_at desc limit 100;

-- 這個組所有「人從卡片下的令」（不屬於任何 campaign）
select created_at, event_type, actor_id, child_run_id, summary, data->>'origin' as origin
from group_agent_events where group_id = '<group id>' and run_id is null
order by created_at desc limit 100;
```

`data.origin` 分得出同一道核准是**從卡片按（`team_card`）、從對話框按（`team_chat`）、還是組代理自己按的（`campaign`）**——事後追查責任時這是三個不同的故事。

事件寫入走 `recordGroupAgentEventSafely`：**記事件失敗不會讓指令失敗**（軌跡是附加價值，不是前置條件）。所以軌跡缺一筆不代表那道指令沒發生，狀態一律以 `group_agent_runs`／`agent_runs` 為準。

### 常見卡住原因怎麼查

| 現象 | 先看 | 通常是什麼 |
|---|---|---|
| campaign 停在 `waiting` | `steps[].status='waiting'` 的那步的 `error`；事件 `step:<id>:budget-hold` / `step:<id>:waiting` | 子計畫估點超出授權（`resumeCampaign` 加授權），或走到 `wait_for_human` 關卡 |
| campaign 一直 `running` 沒進展 | 事件有沒有 `step_started`；server log 有沒有執行器啟動那行 | 子計畫還在跑（正常，`watch` 每 8 秒看一眼）／執行器沒啟動／advisory lock 被另一個 replica 佔著／超過一小時會有 `campaign:stale` |
| `dispatch` 步驟 `failed` | `steps[].error` | 規劃節流（每人每分鐘 4 次）、額度不足、專案已封存、專案不屬於這個組 |
| `watch` 步驟 `failed`，錯誤寫「你已有一個代理在跑」 | 同專案同發起人的其他 run | 併發鎖：一個人在同一專案只能有一份 running/waiting 的計畫 |
| campaign `failed`，error 提到發起人 | 事件 `campaign:authority-lost` | 發起人被停用或被移出組——每輪重驗，不倚賴核准當下那一次 |
| 使用者說「按了停止還在花點」 | 該專案的 `agent_runs` | 正常：停 campaign 不停已派出的子計畫，要各自 `stop_run` |
| 有權的人看不到按鈕／看得到卻按不動 | `teamAssistant.commandLevel` 與 `group_members.agent_command_level` | 前端露出與後端守門讀同一個值；不一致多半是只寫了舊布林那一欄 |

不要手動改 `group_agent_runs.status` 來「修狀態」，也不要刪事件——同〈AI 代理架構與維運〉的規則：狀態修復用新事件與經審核的 migration。

## 已知限制與注意事項

誠實記錄，避免下一個人以為是自己看錯：

1. **前端與後端對「哪些人看得到停止鈕」曾經不一致**（已收斂：兩邊都是「發起人或組長以上」）。若日後改動其中一邊，症狀會是「按下去只吃 FORBIDDEN，看起來像系統壞掉」。
2. **`spentPoints` 記的是估點不是實花。** 授權閘擋的是「自動核准出去的估點總額」，子計畫實際執行可能因重試或模型差異超出估算。畫面上一律標「估」，但要知道這道閘不是硬性支出上限——真正的支出上限仍是組／個人的點數額度。
3. **多副本部署時 `BATCH`（20）份以上同時 running 會有部分計畫要等下一輪**才被推進。執行器會在撈滿時記一筆 warn，且排序改成「最久沒動的先推」，所以不會餓死，但延遲會拉長。

## 幾個一定要知道的執行期性質

這些是實作上刻意處理過的競態與失效模式，改動執行器前務必先讀：

- **停止一定要停得掉。** `settleCampaign` 與 `saveCampaignSteps` 的 UPDATE 都帶狀態 CAS（只在 `running`／`waiting` 時才寫）。沒有 CAS 的話：使用者按下停止的那一刻，執行器可能正卡在一次數十秒的 LLM 規劃裡，回來後會把手上那份「還沒有停止標記」的舊快照連同 `status='running'` 整包蓋回去——計畫復活、繼續自動核准花點，畫面上「已停止」跳回「執行中」。
- **下令之前先落庫。** `executeStep` 把步驟標成 `running` 之後、真正呼叫 `runGroupCommand` 之前先寫一次 `saveCampaignSteps`。不先寫的話，關機（drain 上限遠短於一次 LLM 規劃）剛好落在派工那一步，重開機後該步仍是 `pending`，會再派一次——同一個目標長出兩份待核子計畫，`watch` 只綁得到新的那份，舊的孤兒留在待核清單上占著專案的併發鎖。
- **預算是先預扣再核准。** 兩步不可能原子（核准會提交自己的交易），所以刻意選保守的失敗方向：先用 SQL 端相對增減預扣（`WHERE` 裡再驗一次上限），核准失敗再退回。反過來寫的話，核准成功但記帳失敗會讓 `spentPoints` 留在舊值，其他支線看到「已用 0」繼續核准，一份授權 500 點的計畫可以自動核准掉好幾倍。
- **暫時性阻礙不判死。** 核准撞同專案併發鎖（`CONFLICT`）、派工撞規劃節流（`TOO_MANY_REQUESTS`）都會退回 `pending` 空轉一輪（上限 `MAX_TRANSIENT_WAITS` 輪，之後轉 `waiting` 交給人）。照失敗處理的話，「組長手上剛好在跑一份計畫」這種每天都會發生的事就足以讓整份調度計畫死掉，而前面已核准的子計畫還在燒點。
- **收權每輪重驗。** `advanceCampaign` 每一輪重讀 `agent_command_level`（`loadAuthState` 帶回來的 groups 只有角色、沒有指揮權等級，光看它看不出被降權）。降到 `command` 以下即停止下令。所有 `runGroupCommand` 呼叫傳的是**這一輪讀到的等級**，不是「核准當下驗過就一路通行」。
- **一條支線在等人不會凍結另一條。** run 的 `waiting` 只在 `campaignHasActiveWork` 為 false 時才成立。否則一份「A 支線等授權、B 支線子計畫還在跑」的計畫會被標成 waiting，而執行器只撈 running——B 從此不再被輪詢，已經花錢的子計畫跑完了也不會被標完成。
- **沒有變化就不寫。** `settleCampaign` 在狀態與步驟都沒變時直接返回。這不只是省寫入：`updatedAt` 因此才真的是「最後一次有進展」，所有以「多久沒動」為判準的陳屍偵測才不是死碼。
