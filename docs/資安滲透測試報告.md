## 已確認發現（依嚴重度）

### 1. [HIGH] per-IP登入限流可由偽造 X-Forwarded-For 完全繞過（密碼噴灑/撞庫）

- **攻擊面**：認證與 Session　**端點**：`POST /api/trpc/auth.login`
- **技術**：HTTP header spoofing (X-Forwarded-For) 繞過 IP-based rate limit
- **影響**：per-IP(30次/15分)是唯一阻擋『單一主機大量嘗試』的機制；被繞過後攻擊者可從單一來源對全組織帳號做密碼噴灑/撞庫（每個email仍受5次/15分上限，但可平行嘗試無限多個email、以常見密碼一次撞一輪），大幅提高帳號淪陷風險。單帳號暴力仍受per-email上限保護，故評HIGH而非CRITICAL。
- **PoC**：
```
# A) 固定XFF：第31次被擋(防護原意)
for i in $(seq 1 35); do curl -s -o /dev/null -w "$i:%{http_code} " -X POST 'http://localhost:3000/api/trpc/auth.login?batch=1' -H 'content-type: application/json' -H 'x-forwarded-for: 3.3.3.3' --data "{\"0\":{\"json\":{\"email\":\"ipf-$i@none.test\",\"password\":\"bad\"}}}"; done; echo
# B) 每次換XFF：60次噴灑全部放行、無一被擋
for i in $(seq 1 60); do curl -s -o /dev/null -w "%{http_code} " -X POST 'http://localhost:3000/api/trpc/auth.login?batch=1' -H 'content-type: application/json' -H "x-forwarded-for: 44.0.$i.7" --data "{\"0\":{\"json\":{\"email\":\"rot-$i@none.test\",\"password\":\"bad\"}}}"; done; echo
```
- **觀察證據**：A) 第1..30次回401(UNAUTHORIZED, "email 或密碼不正確")，第31、32次回429(TOO_MANY_REQUESTS, "嘗試太多次，請約 15 分鐘後再試") — 固定IP時per-IP上限30/15分有效。 B) 每請求換一個X-Forwarded-For值時，60次噴灑全部回401，firstBlocked=-1，完全沒有觸發429。程式證據：server/services/auth.ts:25-33 clientIp() 取 x-forwarded-for.split(',')[0]（最左、client可控）；index.ts:42 雖設 app.set('trust proxy',1) 但限流未用 req.ip，故IP鍵完全由攻擊者控制。
- **修法**：限流IP來源改用 Express req.ip（已設 trust proxy=1，會採信任跳數後的真實對端），或在反代層以固定信任的XFF索引取值，勿採用client可控的最左段；並對 auth.login 疊加全域(跨IP)速率上限與漸進延遲/驗證碼作為XFF偽造時的兜底。

### 2. [HIGH] 文件匯入 SSRF：守衛不做 DNS 解析，解析至內網 IP 的 DNS 名稱可繞過（member 可觸發，可達雲端中繼資料/內部服務）

- **攻擊面**：SSRF（文件匯入）　**端點**：`POST /api/trpc/databases.importUrl（及 databases.refreshFile，共用 ssrfGuardError + fetchImport）`
- **技術**：SSRF filter bypass — ssrfGuardError (server/services/databaseFiles.ts:124) 只比對字面 hostname/IP，不解析 DNS。以 *.nip.io / localtest.me 等會解析到 127.0.0.1 或 169.254.169.254 的公開 DNS 名稱送入 url，守衛回 null 放行，fetchImport 依 OS 解析連到內網。
- **影響**：低權限 member 可讓伺服器對任意「DNS 解析至內網」的位址發 GET，並把回應純文字存為資料庫可讀文件（getFileText 讀回）以外洩。可命中雲端中繼資料（169.254.169.254 → IAM 憑證）、內部 HTTP 服務、其他 localhost 埠。redirect 逐跳守衛同樣只檢查字面 IP，故 30x 導到 nip.io 名稱亦可繞過。註：本測試環境因 app 帶 HTTPS_PROXY 出口代理（回 405）恰好擋掉最後一跳，端到端外洩在此環境未觀察到；但守衛層已被繞過、且直連可達性已證實，正式部署（無出口白名單）即為可利用。程式碼註解本身已承認此已知限制（databaseFiles.ts:122「不做 DNS 解析比對」）。
- **PoC**：
```
# 以 Mallory（member）cookie 對其可寫的北區組庫觸發：
curl -s -X POST 'http://localhost:3000/api/trpc/databases.importUrl?batch=1' \
  -H 'content-type: application/json' \
  -H 'cookie: aidos_session=3955f486a2e1f7a3ff589defb6e0bd8ebdf5ef3309cf44578ba72991afbffbee' \
  --data '{"0":{"json":{"tableId":"6cd9cb52-4264-4f76-b880-b030155c002e","url":"http://127.0.0.1.nip.io:3000/api/ready","name":"PENTEST-ssrf"}}}'
# 對照 — 守衛是否放行以錯誤訊息區分：
#   被守衛擋 => "不能匯入內部網址"（如 url=http://127.0.0.1:3000/...）
#   守衛放行、已發出對外抓取 => "抓取失敗（HTTP 405）"（如 nip.io，405 來自出口代理）
# 直連可達性（模擬無出口代理的正式部署）：
curl -s --noproxy '*' http://127.0.0.1.nip.io:3000/api/ready
# 雲端中繼資料變體（DNS 亦可解析到 169.254.169.254）：
#   url=http://169.254.169.254.nip.io/latest/meta-data/
```
- **觀察證據**：守衛放行證據：url=http://127.0.0.1:3000/api/ready 回 400 {code:BAD_REQUEST, message:"不能匯入內部網址"}（守衛擋下）；但 url=http://127.0.0.1.nip.io:3000/api/ready 回 400 {message:"抓取失敗（HTTP 405）..."} —— 訊息不同，代表通過守衛並實際發出對外抓取（405 為 harness 出口代理回應，非 app 守衛）。169.254.169.254.nip.io/latest/meta-data/ 同樣放行（回「抓取失敗 HTTP 405」而非「不能匯入內部網址」）。DNS 解析確認：`getent hosts 127.0.0.1.nip.io` => 127.0.0.1；`socket.gethostbyname('169.254.169.254.nip.io')` => 169.254.169.254。直連可達性確認：`curl --noproxy '*' http://127.0.0.1.nip.io:3000/api/ready` => 200 body {"ok":true,"db":"connected...","mockMode":true,"authMode":"normal"}（回到本機內部服務）。
- **修法**：匯入時解析目的地 IP 後再套用私有網段黑名單（於連線階段檢查已解析位址，非僅字面主機名）：使用釘住已解析 IP 的自訂 dispatcher/agent，或改走出口代理白名單（僅允許 docs.google.com、api.notion.com、drive.google.com 等已知匯入來源網域）；並在每個 redirect 跳點對「已解析 IP」而非字面主機名重跑守衛，以防 DNS rebinding。

### 3. [MEDIUM] 組員可用工作流繞過組長成本核准門檻（approvalThreshold），昂貴生成無審直接扣點送出

- **攻擊面**：商業邏輯/點數/生成　**端點**：`POST /api/trpc/workflows.start?batch=1 （進而 server/services/workflowRunner.ts advanceRun→submitGenerationCore，第 279-288 行，註解明言「不帶 assertAccess」）`
- **技術**：以 workflows.start 觸發 workflowRunner 逐步執行；runner 呼叫 submitGenerationCore 時「不帶 assertAccess」→ accessRole=undefined → generationCore 的 accessRole==='member' 門檻整段被跳過。同一昂貴生成（veo3.1，31 點 ≥ 門檻）直送會被攔成 awaiting_approval，包進工作流卻直接扣點送出。

### 4. [MEDIUM] tRPC 錯誤回應洩漏完整 stack trace 與絕對檔案路徑（NODE_ENV≠production 執行實例）

- **攻擊面**：資訊洩漏/設定/標頭　**端點**：`POST/GET /api/trpc/<proc>`
- **技術**：觸發 tRPC 協定層錯誤（方法不符 / content-type 不符），觀察 error.data.stack
- **影響**：洩漏伺服器絕對檔案系統路徑、tRPC 版本與內部呼叫堆疊，供攻擊者繪製環境指紋。根因：實例以 tsx watch 跑、NODE_ENV 未設為 production，tRPC 預設在非 production 於 error.data 附帶 stack；errorFormatter 僅對 INTERNAL_SERVER_ERROR 遮蔽 message，未移除 stack 欄位。正式（NODE_ENV=production）下 tRPC 不附 stack，故此為部署模式問題。
- **PoC**：
```
curl -sS -X POST 'http://localhost:3000/api/trpc/projects.get?batch=1' -H 'content-type: application/json' --data '{"0":{"json":{"id":"not-a-uuid"}}}'  # 也可：curl -sS -i -X OPTIONS -H 'Content-Type: text/plain' 'http://localhost:3000/api/trpc/auth.logout'
```
- **觀察證據**：HTTP 405，body 含 "code":"METHOD_NOT_SUPPORTED","httpStatus":405,"stack":"TRPCError: Unsupported POST-request... at /home/user/ai_os/node_modules/@trpc/server/src/unstable-core-do-not-import/http/resolveResponse.ts:349:17 ..."。同樣在 415 UNSUPPORTED_MEDIA_TYPE 回應中亦完整帶 stack 與多層 /home/user/ai_os/node_modules/@trpc/... 絕對路徑。
- **修法**：部署一律設 NODE_ENV=production；或在 initTRPC errorFormatter 中一律刪除 shape.data.stack（含 INTERNAL_SERVER_ERROR 分支），不倚賴 NODE_ENV。

### 5. [MEDIUM] Express 預設錯誤處理器對壞 JSON body 回整頁 HTML stack trace（免授權）

- **攻擊面**：資訊洩漏/設定/標頭　**端點**：`POST /api/trpc/* (或任何吃 express.json 的路由)`
- **技術**：送出非法 JSON 請求 body，觸發 body-parser 拋錯 → Express 預設錯誤處理器（dev 模式輸出 stack）
- **影響**：任意未授權來源以一個壞 body 即可取得伺服器絕對路徑與依賴版本（body-parser/raw-body）。根因：無自訂 Express error handler，且 app 非 production，Express 預設 finalhandler 於非 production 輸出 err.stack。tRPC 層的 friendly-message 遮蔽在此路徑（body 解析先於 tRPC）完全繞過。
- **PoC**：
```
curl -sS -X POST 'http://localhost:3000/api/trpc/auth.logout?batch=1' -H 'content-type: application/json' --data 'NOTJSON{{{'
```
- **觀察證據**：回傳 <!DOCTYPE html>...<pre>SyntaxError: Unexpected token 'N', "NOTJSON{{{" is not valid JSON<br> at JSON.parse... at createStrictSyntaxError (/home/user/ai_os/node_modules/body-parser/lib/types/json.js:169:10)<br> at parse (/home/user/ai_os/node_modules/body-parser/lib/types/json.js:90:15) ... /home/user/ai_os/node_modules/raw-body/index.js ...</pre>，完整絕對路徑堆疊。無需任何 cookie/授權。
- **修法**：掛一個放在所有路由之後的自訂 error middleware，統一回 {error:'bad request'} 不含 stack；並設 NODE_ENV=production。

### 6. [MEDIUM] Vite dev server (:5173) 經 /@fs 洩漏全部後端原始碼

- **攻擊面**：資訊洩漏/設定/標頭　**端點**：`GET http://localhost:5173/@fs/<abs-path>`
- **技術**：利用 Vite dev server 的 /@fs/ 檔案服務（workspace root 在 allow 清單內）讀取 client root 以外的伺服器原始碼

### 7. [MEDIUM] 專案「封存」(archived) 後仍可完整寫入並消耗群組點數——封存＝軟刪除卻未凍結任何寫入路徑

### 8. [LOW] 每人 5GB 檔案配額為 read-then-write，併發上傳可能略微超額（TOCTOU）

- **攻擊面**：檔案上傳與儲存　**端點**：`POST /api/databases/upload`
- **技術**：quotaGuardError() 先 userFileUsage()（SELECT sum(sizeBytes)）再於稍後才 INSERT dataFiles，兩步非原子。多個併發請求會讀到相同的 used 值、各自通過檢查後才寫入，總量可超過配額上限
- **影響**：低權使用者可藉併發突發稍微突破個人 5GB 配額，佔用略多磁碟；因單檔 200MB 上限與磁碟水位守門，影響有限。建議在 dataFiles 寫入時以資料庫層原子檢查（例如交易內 SELECT ... FOR UPDATE 彙總或以配額計數列 + 條件式 UPDATE）取代先查後寫。
- **PoC**：

### 9. [LOW] 額度數值欄位超大值（1e308）通過 zod .int() 後於 DB 整數欄位溢位，回 500（輸入驗證缺口）

- **攻擊面**：商業邏輯/點數/生成　**端點**：`POST /api/trpc/quota.setMemberOverride?batch=1（同類亦適用 setMemberBudget/setGroupBudget/updateSettings 等數值欄位）`
- **技術**：z.number().int().min(0) 對 1e308 這類「數學上為整數的浮點」判定通過（Number.isInteger(1e308)===true），未設 .max()／.safe()，直接進 UPDATE 整數欄位造成 DB 溢位錯誤外拋成 500。
- **影響**：非權限或點數膨脹漏洞：此端點需組長／管理權（member 呼叫先被 requireLeader 擋成 403），且結果是查詢失敗而非寫入異常值。屬強健性／輸入驗證缺口——未預期的 500、錯誤訊息洩漏 SQL 片段。建議對所有點數欄位加 .max(合理上限) 或 z.number().int().nonnegative().lt(2**31)。
- **PoC**：
```
POST /api/trpc/quota.setMemberOverride body {"0":{"json":{"groupId":"e5830db6-8eca-488f-b58d-940c8c6cd298","userId":"18603eda-c756-4cd6-a4ab-c6807a034003","weeklyPointsOverride":1e308}}} cookie=adminCookie。
```
- **觀察證據**：回 httpStatus=500 code=INTERNAL_SERVER_ERROR，body 含 'Failed query: update "group_members" set "weekly_points_override" = $1 ...'。對照 -500 則被 zod 正確擋成 400 'Number must be greater than or equal to 0'。
- **修法**：為 quota 相關所有數值輸入加上上限（例如 .max(1_000_000)）並統一以 nonnegative 整數界定，避免溢位值抵達 DB。

### 11. [LOW] CSP 過寬：style-src 'unsafe-inline' 與 img/media/connect 放行整段 https:

- **攻擊面**：資訊洩漏/設定/標頭　**端點**：`全站回應標頭 (helmet CSP)`
- **技術**：檢視回應 Content-Security-Policy 逐項評估
- **影響**：script-src 為 'self' 且無 unsafe-inline/eval——腳本注入防護紮實（正面）。但 connect-src https: 與 img-src https: 放行任意 https 目的地：若他處出現 XSS/注入，資料可經 fetch/img 外洩到任意外部主機（CSP 作為 exfil 防線失效）。style-src 'unsafe-inline' 允許內聯樣式（CSS 注入/有限資料側錄）。屬設定弱化，非可直接利用之漏洞。
- **PoC**：
```
curl -sS -i http://localhost:3000/api/health | grep -i content-security-policy
```
- **觀察證據**：CSP: default-src 'self'; script-src 'self'; script-src-attr 'none'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https:; media-src 'self' data: blob: https:; connect-src 'self' https: wss:; frame-ancestors 'none'; object-src 'none'。
- **修法**：connect-src 收斂到自身 API 網域與必要 fal/nim CDN 白名單而非整段 https:；img/media 同理列白名單；若可行以 nonce/hash 取代 style-src 'unsafe-inline'。

### 12. [LOW] schedule.update 漏掉建立者/組長守衛：一般組員可竄改他人（含組長）建立的組行程

- **攻擊面**：完整性稽核　**端點**：`POST /api/trpc/schedule.update`
- **技術**：授權不一致（Broken Access Control）：getItemChecked() 只做 requireGroup(row.groupId)（同組即過），schedule.update 未加 createdBy/leader 檢查；但同檔的 schedule.remove 正確要求「建立者本人或組長以上」。同一資源的改與刪權限不一致。
- **影響**：組內任一 member 可任意改寫其他成員或組長建立之行程的標題/起訖時間/備註（會反映到 /api/schedule/:groupId/calendar.ics 匯出），造成會議/交付死線被竄改的資料完整性風險與內部社交工程面。侷限於同組（非跨租戶），故列 LOW。
- **PoC**：
```
1) 管理員 Bruce（adminCookie，為 teamNorth 組長）建立行程：POST /api/trpc/schedule.add?batch=1 body {"0":{"json":{"groupId":"e5830db6-8eca-488f-b58d-940c8c6cd298","title":"ADMIN-only meeting","startsAt":"2026-08-01T10:00:00.000Z"}}} → 回 id b0942d35..., createdBy=06163199...(admin)
2) Mallory（memberCookie，teamNorth 純 member、非建立者）竄改：POST /api/trpc/schedule.update?batch=1 body {"0":{"json":{"id":"b0942d35-3d1d-446f-9928-3fa1c8dd10a3","title":"MALLORY-HIJACKED via schedule.update PENTEST"}}}
```
- **觀察證據**：update 回 200，result.data.json 為更新後列：title 變成 "MALLORY-HIJACKED via schedule.update PENTEST"、createdBy 仍為 admin id（06163199...）＝非建立者成功改寫組長建立的行程。對照組：同一 Mallory 對同一 id 呼叫 schedule.remove 回 403 FORBIDDEN「只有建立者本人或組長以上可以刪除行程」——證明改/刪守衛不一致，update 漏防。
- **修法**：schedule.update 比照 schedule.remove：requireGroup 後再檢查 row.createdBy===auth.user.id || role!=='member'，否則 FORBIDDEN；或明確定義組行程為協作共編則在文件與 remove 上一併放寬，讓改/刪語意一致。

### 18. [INFO] X-Frame-Options 為 SAMEORIGIN 而非程式註解宣稱的 DENY（低風險，已被 CSP frame-ancestors 'none' 覆蓋）

- **攻擊面**：資訊洩漏/設定/標頭　**端點**：`全站回應標頭`
