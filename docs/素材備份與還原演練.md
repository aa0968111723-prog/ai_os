# 素材持久性與備份／還原例行演練

> **給誰看**：開發者／維運。  
> **目的**：工具已存在（verify／backup／HTTP tar.gz／Volume 指紋），本文件把它變成**可勾選的週期演練**，避免「有備份卻還原不回來」。  
> **成對原則**：Postgres（中繼資料）與 Volume `/data`（實體檔）必須在**停止寫入的同一 recovery point** 備份與還原——只還一邊＝破圖或孤兒檔；只有同一天檔名不代表一致。

一般維運細節以 [`docs/維運手冊.md`](維運手冊.md) 第二節為準；成對 recovery point、加密、金鑰與卷身分要求以本文件的較嚴格規則為發布閘門。

程式對照：

| 能力 | 位置 |
|------|------|
| 持久判定／卷指紋 | `server/services/storage.ts`（`assessStoragePersistence`、`verifyVolumeIdentity`） |
| 未落地補抓 | `land_state` + `sweepUnlandedAssets` |
| 完整性稽核 | `npm run assets:verify` → `scripts/verify-asset-integrity.ts` |
| 本機／容器備份 | `npm run assets:backup` → `scripts/backup-assets.sh` |
| 線上備份 API | `GET /api/admin/backup/assets.tar.gz`（#306） |
| 備份紀錄 | `backup_runs` → 管理頁 `lastBackupAt` |

## 0. 上線閘門（每次大改／Redeploy 前後）

### 部署前

- [ ] Zeabur App **Volume 掛載路徑為 `/data`**（或 `ASSET_DIR` 指向真實掛載）
- [ ] `APP_URL` 為正式 https 網域（簽名網址／邀請不落入 localhost）
- [ ] `ASSET_SIGN_SECRET` 已固定設定（重啟不換金鑰）
- [ ] `INTEGRATION_TOKEN_SECRET` 已固定設在 Zeabur Variables 並另存於受控 secret manager；不要依賴只存在 Volume、且線上素材 tar 不會包含的 `.integration-key`
- [ ] （建議）`ADMIN_BACKUP_TOKEN` 已設且只放在平台 Variables

### 部署後（15 分內）

- [ ] `GET /api/ready` → `ok: true`，`components.storage` 為持久 Volume 可寫讀（非 fallback）
- [ ] 開發者登入 → 團隊管理「跑系統自檢」儲存層綠
- [ ] 上傳一張小圖 → 記錄 asset id → **Redeploy 一次** → 同一張圖仍可開啟（驗 Volume）
- [ ] （可選）`assets:verify -- --fail-on-missing` 在維運環境對正式 `DATABASE_URL` 抽跑

**失敗即停**：storage 顯示 fallback、或 Redeploy 後圖 404 → 先修掛載，不繼續功能發布。

## 1. 每週演練（約 15–30 分）

**目標**：證明「備份檔產生得出來、異地存得下、管理頁時間有更新」。

### 1.1 健康一瞥

- [ ] 瀏覽器開 `https://你的網域/api/ready`，記錄 `time`、`processRole`、storage 分項
- [ ] 管理頁「素材儲存健康」：無長期紅燈；記下目前 `lastBackupAt`

### 1.2 拉一份素材包（二選一）

**A. HTTP（推薦排程／遠端）**

```bash
curl -fsSL -H "Authorization: Bearer $ADMIN_BACKUP_TOKEN" \
  "https://你的網域/api/admin/backup/assets.tar.gz" \
  -o "aios_assets_$(date +%Y%m%d).tar.gz"
```

**B. UI**：開發者登入 → 團隊管理 → 素材儲存健康 →「立即下載素材備份」

通過標準：

- [ ] HTTP 200；檔案大小 > 0（空站也應有合法 tar 結構）
- [ ] 對下載檔成功執行 `tar -tzf aios_assets_YYYYMMDD.tar.gz >/dev/null`；失敗、截斷或回到 HTML／JSON 錯誤頁都不得標記成功
- [ ] 管理頁 `lastBackupAt` 已更新到本次時間附近
- [ ] 此檔先留在受控 staging；完成 §1.3 的成對、校驗與加密後才可複製到異地

### 1.3 建立一致的 DB＋Volume recovery point（必做）

§1.2 證明「線上素材包下載得出來」，**不能單獨當災難復原備份**。正式 recovery point 必須用以下其中一種方式：

1. Zeabur／儲存供應商能對 DB 與 Volume 建立協調快照時，讓兩者使用同一個 UTC recovery point ID。
2. 否則安排維護窗：停止／縮容所有 web、worker、runner 與上傳寫入者，確認沒有進行中寫入後，在仍能掛載該 Volume 的受控維運工作中執行成對備份；兩份完成校驗後才恢復服務。

維護窗內建議使用同一指令與目錄；`--with-db` 需要可連線的 Postgres URL 與 `pg_dump`：

```bash
RECOVERY_POINT="$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -p "/secure-staging/$RECOVERY_POINT"
OUT_DIR="/secure-staging/$RECOVERY_POINT" \
  DATABASE_URL="$DATABASE_PUBLIC_URL" ASSET_DIR=/data \
  npm run assets:backup -- --with-db

# 卷身分不在 assets tar 內；有檔案時一併保留，避免還原後誤報換卷
test ! -f /data/.volume-id || \
  install -m 600 /data/.volume-id "/secure-staging/$RECOVERY_POINT/volume-id"

# 為 DB、素材與可選的卷身分建立同一份 pair checksum
(
  cd "/secure-staging/$RECOVERY_POINT"
  sha256sum aios_assets_*.tar.gz aios_db_*.dump > pair.sha256
  test ! -f volume-id || sha256sum volume-id >> pair.sha256
)
```

- [ ] 維護窗內沒有 web／worker／runner 寫入；開始與恢復時間已記錄
- [ ] assets tar 與 DB dump 都放在同一 `$RECOVERY_POINT` 目錄，紀錄同一 recovery point ID；禁止混用不同 ID 還原
- [ ] `tar -tzf aios_assets_*.tar.gz >/dev/null` 與 `pg_restore --list aios_db_*.dump >/dev/null` 都成功
- [ ] `.sha256` 驗證成功；若另存 `volume-id`，也將它列入 recovery point manifest

### 1.4 加密、權限與保留（異地前必做）

素材與 DB 可能含使用者媒體、個資與整合中繼資料。離開受控 staging 前，兩者都必須使用組織核准的 KMS／物件儲存 server-side encryption，或用 `age`／GPG 逐檔加密。例如：

```bash
age -r "$BACKUP_AGE_RECIPIENT" -o aios_assets_RECOVERY_POINT.tar.gz.age aios_assets_RECOVERY_POINT.tar.gz
age -r "$BACKUP_AGE_RECIPIENT" -o aios_db_RECOVERY_POINT.dump.age aios_db_RECOVERY_POINT.dump
sha256sum *.age > RECOVERY_POINT.encrypted.sha256
```

- [ ] 解密私鑰只在 secret manager／離線金鑰保管，**不得與備份檔、manifest 或 checksum 放在同一位置**
- [ ] 備份位置只授權指定維運者與還原服務帳號，禁止公開連結與共用個人雲端資料夾
- [ ] 預設保留：每週 8 份、每月 12 份、每季 8 份；法規／合約有更嚴格要求時以其為準
- [ ] 到期由物件儲存 lifecycle 或受稽核刪除工作移除；本機 staging 在上傳與抽樣解密驗證完成後安全刪除
- [ ] `INTEGRATION_TOKEN_SECRET` 固定保存在 secret manager，不放入素材包；若舊部署仍依賴 `/data/.integration-key`，須先把同一值遷移到 Zeabur Variable，或把該檔單獨加密、限制存取並與 recovery point 配對

### 1.5 週紀錄（可貼到維運筆記）

```text

停止／恢復寫入時間：
ready.storage：

```

## 2. 每月演練（約 30–60 分）

**目標**：DB 路徑與磁碟實體一致；未落地 AI 與破圖在可控範圍。

在**維運機或 off-peak** 執行（避免尖峰鎖表／IO）：

```bash
# 破圖或未落地 AI 即非零退出（上線閘門同款）
DATABASE_URL=... ASSET_DIR=/data npm run assets:verify -- --fail-on-missing

# 需要時
DATABASE_URL=... ASSET_DIR=/data npm run assets:verify -- --scan-orphans
DATABASE_URL=... ASSET_DIR=/data npm run assets:verify -- --json > verify_$(date +%Y%m%d).json
```

### 判讀與動作

| 結果 | 意義 | 動作 |
|------|------|------|
| **missingFiles** | DB 有 `storagePath`、磁碟沒檔 | 查 Volume／是否換卷；從最近 assets 備份還原；必要時 `enqueueLanding` 路徑已由程式清謊言 path |
| **unlandedAi** | 仍指 fal 等外部短效 URL | 確認 generation runner／worker 有在跑；查磁碟空間；追蹤 sweep 日誌 |
| **orphans** | 磁碟有、DB 無引用 | 多為軟刪未 purge 或寫入失敗殘檔；**先確認不是還原進行中**再清 |

通過標準：

- [ ] `--fail-on-missing` exit 0，或缺失清單已建票且有修復 ETA
- [ ] Volume 使用率未長期 >80%（面板或 `checkDiskSpace` 行為）
- [ ] 本月至少一組相同 recovery point ID 的 assets + db 加密異地備份仍可下載，且可通過 checksum 與抽樣解密校驗

單元回歸（不需正式 DB）：

```bash
npx vitest run server/services/storage.persist.test.ts
```

## 3. 每季還原演練（手冊 2.5，最重要）

**環境**：本機或隔離 Postgres + 空目錄。**禁止**對正式庫 `pg_restore --clean`。

### 步驟

1. [ ] 選擇**同一 recovery point ID** 的 DB、assets、manifest、checksum 與必要的 volume-id；驗證加密檔 checksum，解密到受控暫存目錄
2. [ ] 準備已建立、可連線且沒有正式流量的空資料庫 `RESTORE_DATABASE_URL`
3. [ ] 還原該 recovery point 的 DB：

   ```bash
   pg_restore --clean --if-exists --no-owner -d "$RESTORE_DATABASE_URL" aios_db_RECOVERY_POINT.dump
   ```

4. [ ] 解壓同一 recovery point 的素材到演練目錄：

   ```bash
   mkdir -p .data && tar xzf aios_assets_RECOVERY_POINT.tar.gz -C .data
   # 確認出現 .data/assets/ ...
   # 有保存 volume-id 時：install -m 600 volume-id .data/.volume-id
   ```

5. [ ] 使用**還原點對應的應用 commit**，確認 `RESTORE_DATABASE_URL` 指向上述已存在且剛完成還原的隔離 DB，再做 migration／drift 檢查；禁止對缺少、過時或正式 DB 執行：

   ```bash
   DATABASE_URL="$RESTORE_DATABASE_URL" npm run db:check
   ```

6. [ ] 啟動。必須注入與原環境相同的 `INTEGRATION_TOKEN_SECRET`；若原環境沒有此變數，則須先還原單獨加密保存的 `.integration-key`：

   ```bash
   # INTEGRATION_TOKEN_SECRET 必須由 secret manager／執行環境注入，不要在指令列輸入值
   DATABASE_URL="$RESTORE_DATABASE_URL" ASSET_DIR="./.data" npm run dev
   ```

7. [ ] 登入 → 專案列表、點數帳本、素材清單與整合連接可讀；抽驗至少一筆既有加密整合憑證可解密／刷新
8. [ ] 執行素材對帳：

   ```bash
   DATABASE_URL="$RESTORE_DATABASE_URL" ASSET_DIR="./.data" \
     npm run assets:verify -- --fail-on-missing
   ```

9. [ ] 若 recovery point 沒保存 `.volume-id`，啟動時出現 `volume-changed` 是預期保護；必須先確認 DB／素材成對、`assets:verify` 綠，再由開發者在系統自檢頁確認「這是刻意還原的新卷」，不得在校驗前直接消警示
10. [ ] UI 抽開 **3–5** 筆圖／影／旁白（含至少一筆 AI 生成落地檔）
11. [ ] 填寫下方「演練紀錄」並存進 `docs/` 以外的維運頻道（勿把連線字串、密鑰或解密金鑰寫進 git）

### 演練紀錄模板

```text
演練日：
recovery point ID（db / assets / volume-id）：
操作者：
還原耗時：
db:check：
verify 結果：
整合憑證抽驗：
UI 抽查 asset ids：
缺漏與原因：
下次改進：
```

通過標準：能登入、verify 綠、抽查媒體可播／可看。任一步失敗 → 當事故預演，修正備份腳本或掛載文件後**兩週內重跑**。

## 4. 災難復原（正式環境，極少動用）

1. 停 App 寫入（Zeabur 暫停／縮容），避免半寫入。
2. 只選用相同 recovery point ID、已通過 checksum 與解密驗證的 DB／assets 配對；禁止混用「同一天」但不同時間窗的檔案。
3. 還原 Postgres 到選定還原點（平台 Backup 或 `pg_restore`）。
4. 還原 Volume：解壓 assets tar 到掛載點，權限與路徑與 `ASSET_DIR` 一致；同步還原 volume-id，或保留稍後人工確認換卷的警示流程。
5. 從 secret manager 注入原本的 `INTEGRATION_TOKEN_SECRET`；若過去依賴 `.integration-key`，先還原其單獨加密備份，否則 DB 內既有整合憑證無法解密。
6. 以**該還原點對應的應用版本**、指向已存在且完成還原之目標 DB 的 `DATABASE_URL` 跑 `npm run db:check`（不要用過新的 migration 硬套舊資料，也不要指向缺少／過時／正式 DB）。
7. 啟動 App → `/api/ready` → 系統自檢 → `assets:verify --fail-on-missing`；全部綠後才確認刻意換卷。
8. 抽樣生成、舊素材與至少一筆整合憑證；點數帳本抽查（見維運手冊 4.3）。

## 6. 常見失敗

| 現象 | 可能原因 |
|------|----------|
| 備份 401 | 未帶開發者 session 或 `ADMIN_BACKUP_TOKEN` |
| `lastBackupAt` 不更新 | 備份 API 未走完整成功路徑／未寫 `backup_runs` |
| Redeploy 後全站破圖 | Volume 未掛或掛到非持久層；映像內 `/data` 假目錄 |
| verify 大量 unlandedAi | worker／runner 未跑、磁碟滿、外部 URL 過期 |
| 只還原 DB | 全部 storagePath 指到空磁碟 → 必須成對還 Volume |
| DB 有整合連接但全部解密失敗 | 還原時換了 `INTEGRATION_TOKEN_SECRET`，或舊部署的 `.integration-key` 未另行保存／還原 |
| 還原後顯示 volume-changed | `.volume-id` 不在 assets tar；先驗證成對 recovery point 與素材完整性，再由開發者確認刻意換卷 |
