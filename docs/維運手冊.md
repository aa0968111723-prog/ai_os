## 一、Schema 變更（改資料表）風險與守則

### 1.1 現況：pushSchema「直推」，沒有 migration 檔

資料表結構的唯一真相是 `server/db/schema.ts`。同步到資料庫有兩條路，行為等價：

| 場景 | 機制 | 特性 |
|---|---|---|
| 本機開發 | `npm run db:push`（drizzle-kit push CLI） | **互動式**：有風險的變更會在終端機提問確認 |
| 正式站（Railway） | 容器啟動時 `server/db/ensure.ts` 自動跑 `pushSchema`（drizzle-kit/api） | **非互動**：比對 schema.ts 與 DB 差異後直接套用，結果印在 Deploy Logs（中文） |

「直推」的意思：程式看到 schema.ts 和資料庫不一樣，就直接下 CREATE/ALTER 把資料庫改成一樣。
**沒有版本紀錄、沒有 down migration、不能回滾**——回滾唯一的手段是備份（第二節）。

### 1.2 哪些變更安全、哪些危險

| 變更類型 | 風險 | 說明 |
|---|---|---|
| 新增表、新增欄位（nullable 或有 default）、新增普通 index | ✅ 安全 | 直接 CREATE，不動既有資料（repo 內既有做法都刻意走這型，schema.ts 註解可見） |
| 欄位／表**改名** | ⚠️ 危險 | push 分不出「改名」和「刪舊建新」→ 可能**舊欄資料全丟**；CLI 會提問，容器版列入資料遺失防護 |
| 型別**收緊**（text→integer、縮長度） | ⚠️ 危險 | 既有資料轉不過去會失敗，CLI 可能問「要不要 truncate」——正式資料上絕不可答應 |
| 對既有欄位加 **unique / not null** | ⚠️ 危險 | 既有資料有重複或 NULL 就套用失敗；CLI 走互動提問（非 TTY 的容器裡曾因此靜默失敗，這正是啟動改用 pushSchema API 的原因，見 ensure.ts 檔頭註解） |
| DROP TABLE / DROP COLUMN | 🚫 高危 | 正式站有保險絲（見下），本機請自己三思 |

**正式站的保險絲**：`ensure.ts` 偵測到 `hasDataLoss` 或 SQL 含 DROP COLUMN/TABLE 時，**預設跳過套用**、
只在 Deploy Logs 印警告與該段 SQL，其餘功能照常啟動。確認無誤真要套用，設環境變數
`ALLOW_DB_DATALOSS=1` 後 Redeploy——**用完立刻移除**，不要長期留著這條引線。

### 1.3 上線後改 schema 的建議流程

1. **本機演練**：本機 Postgres 開一個庫（有條件就灌一份正式站備份進去），改完 schema.ts 跑
   `npm run db:push`，看有沒有互動提問或資料遺失警告——這裡看到的問題，上線一定也會遇到
2. **備份正式庫**：改表前必做一次 `pg_dump`（指令見 2.3）——這是唯一的回滾手段
3. **部署**：push 上去讓 Railway 建置；盯 Deploy Logs 出現「✓ 資料表同步完成（套用 N 項變更）」，
   若出現「⚠⚠⚠ 偵測到可能造成資料遺失」就停下來回 1.2 對照
4. **驗證**：開 `/api/ready` 確認資料庫接通 → 登入 → 團隊管理「跑系統自檢」七項全 ✅

危險變更（改名／收緊型別／加 unique）不要一步到位——改成兩段式：
**加新欄 → 程式雙寫並回填 → 確認資料齊了 → 下一個版本再刪舊欄**，每段之間至少隔一個部署週期。

### 1.4 未來導入正式 migration 檔的路徑

資料量變大、多人共同維運後，建議升級成 migration 檔工作流。路已鋪好（`drizzle.config.ts`
已設 `out: "./drizzle"`）：

1. `npx drizzle-kit generate`——依 schema.ts 差異產出帶版本號的 SQL 檔到 `drizzle/`，進 git 供審閱
2. 部署改跑 `npx drizzle-kit migrate`（或程式內 `migrate()`），取代 ensure.ts 的 pushSchema
3. **記得改 Dockerfile**：目前 runner 階段只複製 `schema.ts`＋`drizzle.config.ts`、刻意**沒帶 drizzle/**
   （Dockerfile 內有註解），切換時要補 `COPY drizzle/ ./drizzle/`
4. 首次切換前先對既有 DB 做基線：既有表已存在，第一份 migration 要能被視為「已套用」
   （空跑或用 drizzle 的 baseline 作法），否則 migrate 會想重建所有表

## 二、備份與還原

### 2.1 要備的東西有「兩份」，必須成對

| 資料 | 位置 | 內容 |
|---|---|---|
| 資料庫 | Railway **Postgres 服務** | 帳號、專案、世界觀、點數帳本、審計日誌、知識庫，以及**素材的中繼資料（assets.storagePath）** |
| 素材檔 | Railway **Volume**（掛在 App 服務的 `/data`） | 上傳與生成的實體檔：`assets/YYYY/MM/uuid.ext`、回饋截圖 `assets/feedback/`（`tmp/` 是暫存不用備） |

DB 裡的 `assets.storagePath` 記的是 Volume 內相對路徑——**只還原 DB 素材全變破圖；
只還原 Volume 檔案全成孤兒**。備份要在同一時間窗成對做，還原也要成對還原。

### 2.2 Railway 每日備份確認方式

- **Postgres**：Railway 面板 → Postgres 服務 → **Backups** 分頁：確認每日備份排程有開、
  看得到最近成功的備份點、保留天數符合需求（依方案不同）；還原是在同一分頁對備份點按 Restore
- **Volume**：App 服務掛載的 Volume 設定頁查看有無快照／備份功能（各方案支援度不同）；
  沒有就靠 2.4 手動打包
- **不要只信面板**：面板顯示「有備份」不等於「還原得回來」——每季照 2.5 實際演練一次

### 2.3 手動備份／還原資料庫（pg_dump / pg_restore）

在本機終端機執行（需安裝 postgresql-client）。**連線字串注意**：App 服務內的 `DATABASE_URL`
是 `*.railway.internal` 內網位址，本機連不到——要用 Postgres 服務 **Connect 分頁的
Public Network 連線字串**（或 `DATABASE_PUBLIC_URL` 變數）。

```bash
# 備份：自訂壓縮格式（-Fc），之後可選擇性還原單表
pg_dump "$DATABASE_URL" -Fc -f aios_$(date +%Y%m%d).dump

# 還原到「另一個空庫」驗證（平常演練都這樣做，不碰正式庫）
pg_restore --clean --if-exists --no-owner -d "$RESTORE_DATABASE_URL" aios_20260716.dump

# 想看得懂內容：輸出純 SQL 版（可直接 psql 匯入）
pg_dump "$DATABASE_URL" > aios_backup.sql
```

真要對**正式庫**還原（災難復原）：先把 App 服務停掉（避免邊還原邊寫入）→ `pg_restore` →
重啟 App（啟動時 pushSchema 會自動核對表結構）→ `/api/ready`＋系統自檢確認。

### 2.4 Volume（/data 素材）備份注意

- 有 Railway CLI 且支援 ssh 時，可整包拉回本機：
  `railway ssh "tar czf - /data/assets" > aios_assets_$(date +%Y%m%d).tar.gz`
- 或使用面板的 Volume 快照功能（若方案有）
- 素材是「軟刪除」（回收桶不刪 Volume 檔），Volume 上的檔案通常比 DB 目前引用的多——正常現象
- 備份頻率建議跟 DB 對齊（至少每週一次、改動大時加做），並和當日的 DB dump 放在一起保存

### 2.5 還原演練（建議每季一次）

1. 本機建空 Postgres → `pg_restore` 最近一份備份
2. `DATABASE_URL=<演練庫> npm run dev` 起本機站 → 能登入、專案／點數帳本／素材清單都在
3. 抽查 3–5 筆素材：把成對備份的 Volume 檔放回 `./.data/assets/` 對應路徑，確認開得起來
4. 記錄演練結果（備份日期、還原耗時、缺漏）——真出事時這張紀錄就是 SOP

## 三、環境變數清單（以 .env.example 為準）

| 變數 | 用途 | 風險／注意 |
|---|---|---|
| `DATABASE_URL` | Postgres 連線字串（Railway 用 Add Reference 引用 Postgres 服務） | 沒設：伺服器照起、健檢照過，但登入與所有資料操作失敗。等同資料庫鑰匙，**絕不進 git／截圖** |
| `FAL_KEY` | Fal.ai 金鑰（媒體生成：圖像/影片/音訊/視覺/轉錄/訓練）——**必填** | **設了就是真金白銀**：外洩＝別人花你的錢。只放部署平台 Variables；沒設不再退示範模式——生成回明確錯誤並自動退點 |
| `NVIDIA_NIM_API_KEY` | NVIDIA NIM 金鑰（LLM 文字生成：導演/助手/彙總/生成台 LLM 類） | 同為**真金白銀**，只放 Railway Variables；沒設→真實模式下 LLM 功能回明確錯誤並自動退點。連線自檢：`npx tsx scripts/check-nim.ts` |
| `E2E_MOCK` | `1`＝全站假生成（LLM 的 NIM 呼叫同受守門）——**僅供 CI/本機自動化測試** | 正式部署**絕不設定**：設了＝夥伴以為在真生成,實際拿到假素材。舊旗標 FAL_MOCK 已移除、不再生效 |

## 四、緊急應變

### 4.1 網站起不來／開了一片空白

1. 瀏覽器開 `你的網址/api/ready`——中文告訴你「資料庫接通了沒、初始化完成沒」
2. 沒接通：九成是 `DATABASE_URL` 沒用 Add Reference 引用 Postgres → 修 Variables → Redeploy
3. 看 Deploy Logs（全中文）：`[db] 等待資料庫就緒（n/10）`＝DB 慢啟動；初始化失敗時伺服器
   **每 60 秒自動重試**，多等一下常常自己好
4. Logs 出現「⚠⚠⚠ 偵測到可能造成資料遺失的 schema 變更——已跳過套用」：這次部署帶了
   危險 schema 變更，回第一節 1.2／1.3 處理，不要直接設 ALLOW_DB_DATALOSS
5. `/api/health` 有回、`/api/ready` 失敗＝服務活著但 DB 掛了：查 Railway Postgres 服務
   狀態、方案額度是否用盡被停

### 4.2 生成全部失敗

1. 先確認 `FAL_KEY` 有設且有效（正式站一律真實模式；`/api/ready` 的 `mockMode` 恆為 false，true 只會出現在 e2e 測試環境）
2. 上 fal.ai 儀表板：**金鑰還有效嗎？餘額／額度用完了嗎？**（FAL_KEY 失效或欠費＝媒體模型齊failed）
3. 只有「LLM／AI 助手類」失敗（媒體生成正常）：查 NVIDIA NIM——跑 `npx tsx scripts/check-nim.ts`
   自檢金鑰與端點；NVIDIA_NIM_API_KEY 失效或額度用盡＝導演建議/拆分鏡/助手/生成台 LLM 類齊 failed
4. 只有「特定幾個模型」失敗：多半是 `verified=false` 的推測 model id 不存在（見第五節），
   對照 shared/models.ts 與 fal 模型頁（LLM 類對照 build.nvidia.com）修正 id
5. 止血：示範模式已移除，正式站沒有「假生成頂著」的選項——請直接修復金鑰／額度（失敗的生成都會自動退點，夥伴不會白扣）
6. 失敗的生成會自動全額退點；若 Logs 出現 `[CRITICAL] 退點失敗（已重試 3 次，需人工補點）`，
   記下 user／points，照 4.3 對完帳後人工補點

### 4.3 點數異常（帳對不上）

帳本規則：`cost_ledger.delta` **扣點為負、退點為正**，淨消耗＝`-SUM(delta)`。
用 Railway Postgres 的 Data／Query 面板（或 psql）跑：

```sql
-- A. 全站淨消耗（應與管理頁顯示一致）
SELECT -SUM(delta) AS 淨消耗 FROM cost_ledger;

-- B. 當月每人消耗排行（消耗突增一眼看到）
SELECT user_id, -SUM(delta) AS 當月淨扣點, COUNT(*) AS 筆數
FROM cost_ledger
WHERE created_at >= date_trunc('month', now())
GROUP BY user_id ORDER BY 當月淨扣點 DESC;

-- C. 淨額為「正」的生成＝退點多於扣點，必有異常
SELECT generation_id, SUM(delta) AS 淨額
FROM cost_ledger WHERE generation_id IS NOT NULL
GROUP BY generation_id HAVING SUM(delta) > 0;

-- D. 已失敗卻沒退乾淨的生成（該人工補退的名單）
SELECT g.id, g.model_id, g.user_id, c.淨額
FROM generations g
JOIN (SELECT generation_id, SUM(delta) AS 淨額 FROM cost_ledger GROUP BY generation_id) c
  ON c.generation_id = g.id
WHERE g.status = 'failed' AND c.淨額 < 0;

-- E. 對照審計日誌：某人某天做過什麼（actor_id 填 users.id）
SELECT created_at, action, ok, error
FROM audit_log
WHERE actor_id = '<userId>' AND created_at >= current_date
ORDER BY created_at;
```

人工補點：比照程式的退點寫法，插入一筆**正 delta**、reason 註明人工補點與原因，
之後 A／B 口徑自動一致。

### 4.4 fal 月帳單對帳（每月一次）

1. fal.ai 儀表板下載當月帳單總額（USD）
2. 跑 4.3 的 B（把 `user_id` 拿掉就是全站當月淨扣點）
3. 帳單 USD × 匯率（點數校準用 31，見 docs/點數校準報告.md 檔頭）↔ 當月淨扣點（1 點≈NT$1）對比
4. 毛差大（例如 >20%）：對照 docs/點數校準報告.md「建議優先校準」表——**「偏低」的模型長期會虧**，
   改 `shared/models.ts` 的 `points` → 重新部署（啟動 `syncCatalog()` 自動同步、工作流總點數自動重算）
5. 改完點數重跑 `npx tsx scripts/audit-model-pricing.ts` 與 `npx tsx scripts/gen-model-docs.ts`，
   讓兩份文件與程式保持同步

## 五、例行維護（每月清單）

| 頻率 | 事項 | 做法 |
|---|---|---|
| 每月 | 點數校準 | `npx tsx scripts/audit-model-pricing.ts` 重生 docs/點數校準報告.md，處理「偏低」模型；搭配 4.4 對 fal 帳單 |
| 每月 | 檢查 `verified=false` 模型 | shared/models.ts 中標 false 的是「合理推測 id」，真實模式首跑可能失敗——有 FAL_KEY 後逐一實測，測過改 true |
| 每月 | 磁碟空間 | 程式守門邏輯（storage.ts `checkDiskSpace`）：可用空間低於 **64MB 水位就拒收新檔**、單檔上限 `ASSET_MAX_MB`（預設 200MB）。Railway 面板看 Volume 使用率，>80% 就擴容或清理回收桶素材 |
| 每月 | 備份抽查 | Railway Backups 分頁有最近備份點＋手動抓一份 pg_dump 存異地 |
| 每季 | 還原演練 | 照 2.5 完整走一遍並記錄 |
| 每季 | 帳號與金鑰盤點 | 停用離開的成員（users.status）、確認 SEED_ADMIN_PASSWORD 已設強密碼、Railway 面板成員最小化、MCP_API_KEY 不用就清空 |
