## 一、Schema 變更（改資料表）風險與守則

### 1.1 現況：migration-first

資料表宣告的單一真相是 `server/db/schema.ts`，已審核的變更歷史在 `drizzle/`。正式站流程為：

1. release／one-off job 明確執行 `npm run db:migrate`
2. `npm run db:check` 驗證 ledger hash、連續性與 live schema drift
3. Web 容器才啟動；`start.sh` 與 `ensure.ts` 都只讀檢查，絕不 runtime push DDL

空 DB 與既有 DB 首次 baseline 的逐步指令、fingerprint 確認與回滾方式，統一見
[`docs/資料庫遷移.md`](資料庫遷移.md)。

### 1.2 哪些變更安全、哪些危險

| 變更類型 | 風險 | 說明 |
|---|---|---|
| 新增表、新增欄位（nullable 或有 default）、新增普通 index | ✅ 安全 | 直接 CREATE，不動既有資料（repo 內既有做法都刻意走這型，schema.ts 註解可見） |
| 欄位／表**改名** | ⚠️ 危險 | 產生 SQL 後必須人工確認是 rename，不可接受「刪舊建新」 |
| 型別**收緊**（text→integer、縮長度） | ⚠️ 危險 | 既有資料可能轉換失敗；先做可重複的 preflight 查詢與回填 |
| 對既有欄位加 **unique / not null** | ⚠️ 危險 | 先查重複／NULL，明確定義修復與保留規則，再建立約束 |
| DROP TABLE / DROP COLUMN | 🚫 高危 | 必須走 expand/backfill/contract，並附 migration 前備份與還原演練 |

### 1.3 上線後改 schema 的建議流程

1. 改 `schema.ts` 後跑 `npm run db:generate -- --name=<短名>`，migration SQL 與 meta 一起審查。
2. 把正式備份還原到隔離 DB，跑 `db:migrate:dry-run`、`db:migrate`、完整測試與 `db:check`。
3. 正式庫 migration 前做 `pg_dump`（指令見 2.3），記錄還原命令與停止條件。
4. release job 單例執行 `db:migrate`；成功後才滾動 App，最後驗證 `/api/ready` 與系統自檢。

危險變更（改名／收緊型別／加 unique）不要一步到位——改成兩段式：
**加新欄 → 程式雙寫並回填 → 確認資料齊了 → 下一個版本再刪舊欄**，每段之間至少隔一個部署週期。

### 1.4 不可變歷史與回滾

已在共享環境套用的 SQL 不可修改；啟動檢查會以 SHA-256 ledger fail closed。修正一律新增下一份
migration。沒有通用 down migration：優先 roll-forward，或回滾到仍相容新 schema 的應用版本；
破壞性資料錯誤則停寫並還原 migration 前備份。完整決策樹見資料庫遷移 Runbook 第六節。

## 二、備份與還原

> 現行平台是 **Zeabur**（2026-07 前在 Railway）。以下指令都在你自己的電腦或外部排程機器上跑，
> 不依賴任何平台專屬 CLI；素材備份走系統內建端點，平台換了也照樣能用。

### 2.1 要備的東西有「兩份」，必須成對

| 資料 | 位置 | 內容 |
|---|---|---|
| 資料庫 | Zeabur 專案內的 **PostgreSQL 服務** | 帳號、專案、世界觀、點數帳本、審計日誌、知識庫，以及**素材的中繼資料（assets.storagePath）** |
| 素材檔 | **Volume**（掛在 App 服務的 `/data`） | 上傳與生成的實體檔：`assets/YYYY/MM/uuid.ext`、回饋截圖 `assets/feedback/`（`tmp/` 是暫存不用備） |

DB 裡的 `assets.storagePath` 記的是 Volume 內相對路徑——**只還原 DB 素材全變破圖；
只還原 Volume 檔案全成孤兒**。備份要在同一時間窗成對做，還原也要成對還原。

### 2.2 資料庫備份（Zeabur PostgreSQL 服務）

- Zeabur Dashboard → 你的專案 → **PostgreSQL 服務** → 服務頁的 **Backups（備份）**：
  確認排程是開的、看得到最近一次成功的備份點、保留份數符合需求（依方案不同）；
  還原也在同一處對備份點操作。
- **方案沒有排程備份功能就不能只靠平台**：改成用 2.3 的 `pg_dump` 定期抓一份存到別的地方
  （建議至少每週一次，並和當週的素材備份放在一起）。
- **不要只信面板**：顯示「有備份」不等於「還原得回來」——每季照 2.6 實際演練一次。
- 備份與素材備份要**存在平台之外**（自己的電腦／另一家雲端硬碟）。備份跟正式站放同一個帳號下，
  帳號出事就兩份一起沒了。

### 2.3 手動備份／還原資料庫（pg_dump / pg_restore）

在本機終端機執行（需安裝 postgresql-client 16）。**連線字串注意**：App 服務裡的 `DATABASE_URL`
通常是 Zeabur 專案內網位址，你的電腦連不到——要到 **PostgreSQL 服務 → Networking／Connect**
開啟公開連線（Public）並複製那一串公開連線字串來用。備份完記得把公開連線關回去。

```bash
# 備份：自訂壓縮格式（-Fc），之後可選擇性還原單表
pg_dump "$DATABASE_URL" -Fc -f aios_$(date +%Y%m%d).dump

# 還原到「另一個空庫」驗證（平常演練都這樣做，不碰正式庫）
pg_restore --clean --if-exists --no-owner -d "$RESTORE_DATABASE_URL" aios_20260716.dump

# 想看得懂內容：輸出純 SQL 版（可直接 psql 匯入）
pg_dump "$DATABASE_URL" > aios_backup.sql
```

真要對**正式庫**還原（災難復原）：先把 App 服務停掉（避免邊還原邊寫入）→ `pg_restore` →
以還原點對應的 commit 執行 `npm run db:check` → 重啟 App → `/api/ready`＋系統自檢確認。

### 2.4 素材（/data）備份：系統內建的一鍵下載

平台沒有 Volume 快照時，素材就得靠系統自己提供的備份端點。**兩種用法，備出來的東西一樣**：

- **人工（平常用這個）**：開發者登入 → **團隊管理頁 → 按「立即下載素材備份」** →
  瀏覽器下載 `assets.tar.gz`。下載完把它搬到平台以外的地方保存。
- **外部排程（建議設定）**：先在部署平台設環境變數 `ADMIN_BACKUP_TOKEN`（長隨機字串），
  再讓你自己的排程機器每天／每週跑：

  ```bash
  curl -fsS -H "Authorization: Bearer $ADMIN_BACKUP_TOKEN" \
    "https://你的網域/api/admin/backup/assets.tar.gz" \
    -o "aios_assets_$(date +%Y%m%d).tar.gz"
  ```

  ⚠ 這把權杖等同「整包素材下載權」：只放環境變數與排程機器的密鑰設定，不要寫進網址查詢字串
  （會被各層存取紀錄留下來），也不要進 git。

**包裡的 `manifest.json` 是什麼、有什麼用**：它列出這次備份的每個檔案（相對路徑、大小、雜湊）
與總檔數／總位元組。用途是**還原後拿它逐項比對**——檔數對不對、大小對不對，
不用靠「看起來好像都在」這種感覺驗收（比對步驟見 2.5）。

其他要知道的：

- 素材是**軟刪除**（回收桶不會刪 Volume 上的檔），所以備份包裡的檔案通常比 DB 目前引用的多——正常現象。
- 備份頻率跟 DB 對齊（至少每週一次、素材改動大時加做），**和當日的 DB dump 放在一起**保存，
  這樣才還原得回成對的狀態。
- 「上次成功備份是什麼時候」不用自己記：系統自檢有一項 **「素材備份新鮮度」**，
  超過 48 小時沒有成功備份就會直接亮紅（並附上一次備份的時間、檔數與大小）。

### 2.5 還原素材（把備份包放回 Volume）

1. **先確認 Volume 已掛在 App 的 `/data`**（Zeabur → App 服務 → Settings → Volumes）。
   沒掛就先掛：不然檔案放進去，下一次重新部署又整批消失。
2. 用 Zeabur 的 Web Terminal（或一次性 shell）把備份包放進去解開。**目錄結構要對齊**：
   包內若是 `assets/YYYY/MM/...` 就解到 `/data`；包內若直接是 `YYYY/MM/...` 就解到 `/data/assets`。

   ```sh
   tar xzf aios_assets_20260801.tar.gz -C /data      # 或 -C /data/assets，視包內結構
   ls /data/assets                                    # 應該看得到 2026 這種年份資料夾與 feedback/
   ```
3. **用 `manifest.json` 驗收**：確認檔數與總大小和 manifest 記的一致；有落差就記下少了哪些路徑。
4. 回系統跑一次**系統自檢**，看 **「素材檔抽樣完整性」** 是否轉綠（它會拿資料庫的紀錄去對磁碟上的
   實體檔，缺檔或大小對不上都會報出來，並附幾筆樣本讓你知道是哪些）。
5. 如果這次還原**換了新的 Volume**（不是原本那顆），全站會出現「儲存空間可能被更換」的紅色橫幅——
   確認過檔案都放回去了之後，在橫幅上按「我已了解」重設指紋，警示才會解除。

### 2.6 還原演練（建議每季一次）

1. 本機建空 Postgres → `pg_restore` 最近一份備份
2. `DATABASE_URL=<演練庫> npm run dev` 起本機站 → 能登入、專案／點數帳本／素材清單都在
3. 抽查 3–5 筆素材：把**同一時間窗**的素材備份解到 `./.data/assets/` 對應路徑，確認圖／影片開得起來
4. 記錄演練結果（備份日期、還原耗時、缺漏）——真出事時這張紀錄就是 SOP

## 三、環境變數清單（以 .env.example 為準）

| 變數 | 用途 | 風險／注意 |
|---|---|---|
| `DATABASE_URL` | Postgres 連線字串（Zeabur 用變數參照引用同專案的 PostgreSQL 服務） | 沒設：正式容器拒絕啟動。等同資料庫鑰匙，**絕不進 git／截圖** |
| `FAL_KEY` | Fal.ai 金鑰（媒體生成：圖像/影片/音訊/視覺/轉錄/訓練）——**必填** | **設了就是真金白銀**：外洩＝別人花你的錢。只放部署平台 Variables；沒設不再退示範模式——生成回明確錯誤並自動退點 |
| `NVIDIA_NIM_API_KEY` | NVIDIA NIM 金鑰（LLM 文字生成：導演/助手/彙總/生成台 LLM 類） | 同為**真金白銀**，只放部署平台 Variables；沒設→真實模式下 LLM 功能回明確錯誤並自動退點。連線自檢：`npx tsx scripts/check-nim.ts` |
| `E2E_MOCK` | `1`＝全站假生成（LLM 的 NIM 呼叫同受守門）——**僅供 CI/本機自動化測試** | 正式部署**絕不設定**：設了＝夥伴以為在真生成,實際拿到假素材。舊旗標 FAL_MOCK 已移除、不再生效 |
| `TOTAL_BUDGET_POINTS` | 總預算點數「初始值」（預設 5000） | **只在首次啟動寫入 DB**，之後改這變數沒有效果——請在系統「團隊管理→點數與額度」調 |
| `WEEKLY_QUOTA_POINTS` | 每人每週額度「初始值」（預設 300） | 同上：首啟後一律在系統內調 |
| `SEED_ADMIN_EMAIL` | 種子開發者帳號 email（程式內建預設 aa0968111723@gmail.com） | 與下一項合起來是「忘記密碼萬能自救」：設好 → Redeploy 即可用此帳密登入 |
| `SEED_ADMIN_PASSWORD` | 種子開發者密碼 | **高危**：能看部署平台 Variables 的人＝能拿最高權限。上線穩定後設強密碼，並收緊 Zeabur 專案的成員名單 |
| `RATE_LIMIT_SECRET` | 登入、MCP 與 AI／外部抓取限流鍵的 HMAC-SHA-256 金鑰 | **production 必填且至少 32 字元**；所有 replicas 必須相同並跨重啟固定。原始 email/IP 不落 DB。遺失／輪替會等同清空短期限流窗，不會影響帳號或內容資料 |
| `AUTH_MODE` | `dev`＝跳過登入（自動以開發者身分） | **後門等級**，只限本機開發測功能。production 下程式會忽略，但任何雲端環境都不要設 |
| `APP_URL` | 對外正式網址（邀請連結、素材簽名網址用） | 填錯：邀請連結指向錯的網址、fal 抓不到來源素材 |
| `MCP_API_KEY` | 舊共用超管金鑰，只供非 production 本機／CI；正式站會忽略 | 正式站不要設定；外部 AI 改用每位成員自行建立、可撤銷與可到期的個人連線金鑰 |
| `ASSET_DIR` | 素材儲存根目錄（空＝/data 是真正的掛載點就用它，否則退回 ./.data） | Volume 掛在別的路徑又沒設＝檔案寫進容器磁碟，重佈整批消失（系統會亮紅，但檔案救不回來） |
| `ASSET_PERSISTENT` | 覆寫持久性判定：`1`＝這個路徑確定是持久卷、`0`＝強制當成非持久 | 空＝自動偵測（判掛載點）。**只有在明明掛了卷卻被誤判**時才設 1；不要拿它「消警告」，那等於自己關掉守門 |
| `ASSET_STRICT` | `1`＝偵測到非持久／不可寫／卷被換掉時，直接拒收新素材 | 預設只警告不攔。設 1 前先確認偵測在你的環境判斷正確，否則誤判會讓正常站台變唯讀 |
| `ASSET_MAX_MB` | 上傳／落地單檔上限 MB（預設 200） | 太小＝大成品落不了地，只能沿用會過期的外部網址。Volume 擴容後調大即可，免改碼 |
| `ASSET_SIGN_SECRET` | 素材簽名網址金鑰；**正式站必設** | 沒設則每次重啟金鑰重生，在途簽名網址全部失效（排隊中的生成抓不到來源素材）。設一次就不要換 |
| `ASSET_LAND_MAX_ATTEMPTS` | 成品落地（抓回 Volume）失敗的最大重試次數 | 空＝內建預設。超過次數的會退出補抓佇列並標記失敗，避免死列佔滿名額；剩幾筆看自檢「未落地素材」 |
| `ADMIN_BACKUP_TOKEN` | 素材備份端點 `/api/admin/backup/assets.tar.gz` 的存取權杖（外部排程用） | **等同整包素材下載權**：只放平台 Variables 與排程機器密鑰設定，不放網址查詢字串、不進 git。沒設＝只能人工下載 |

## 四、緊急應變

### 4.1 網站起不來／開了一片空白

1. 瀏覽器開 `你的網址/api/ready`——中文告訴你「資料庫接通了沒、初始化完成沒」
2. 沒接通：九成是 `DATABASE_URL` 沒正確引用同專案的 PostgreSQL 服務 → 修 Variables → Redeploy
3. 看 Deploy Logs：`state=empty-unmigrated`／`pending` 時由 release job 跑 `db:migrate`；
   `legacy-untracked` 走 baseline Runbook；`invalid`／`schema drift` 必須人工診斷，程式不會偷偷修。
4. `start.sh` 的 `db:check` 失敗會以 exit 78 停止，避免不相容版本接流量；不要把 gate 移除止血。
5. `/api/health` 有回、`/api/ready` 失敗＝服務啟動後 DB 掛了：查 Zeabur 專案裡 PostgreSQL
   服務的狀態、方案額度是否用盡被停
6. 登入／MCP／AI 助手回「安全限流暫時無法使用」：系統正確地 **fail closed**，不會退回單機
   計數器。先查 Postgres，再確認所有 App replicas 都有同一把、至少 32 字元的
   `RATE_LIMIT_SECRET`；不要為了止血移除限流。

限流狀態在 `rate_limit_buckets`，只存用途 scope、HMAC key 與短期時間戳／封鎖期限；不存原始
email、IP 或 user id，request nonce 也完全不進限流狀態。登入為 email 5 次/15 分鐘及 IP
30 次/15 分鐘的滑動視窗；MCP 金鑰每 IP 1 分鐘內第 10 次失敗後封鎖 5 分鐘；AI 與外部抓取
各保留原有每人上限。專案助手即使以同一 nonce 從 SSE 退回 tRPC，每個外部呼叫仍各自計次；
在沒有原子結果快取前不提供免計捷徑，避免惡意並行請求倍增付費模型吞吐。
成功登入會清除自己的 email 桶並只回收該次 IP 命中，成功 MCP 驗證則清除該 IP 的失敗桶。

### 4.2 生成全部失敗

1. 先確認 `FAL_KEY` 有設且有效（正式站一律真實模式；`/api/ready` 的 `mockMode` 恆為 false，true 只會出現在 e2e 測試環境）
2. 上 fal.ai 儀表板：**金鑰還有效嗎？餘額／額度用完了嗎？**（FAL_KEY 失效或欠費＝媒體模型齊failed）
3. 只有「LLM／AI 助手類」失敗（媒體生成正常）：查 NVIDIA NIM——跑 `npx tsx scripts/check-nim.ts`
   自檢金鑰與端點；NVIDIA_NIM_API_KEY 失效或額度用盡＝導演建議/拆分鏡/助手/生成台 LLM 類齊 failed
4. 只有「特定幾個模型」失敗：多半是 `verified=false` 的推測 model id 不存在（見第五節），
   對照 shared/models.ts 與 fal 模型頁（LLM 類對照 build.nvidia.com）修正 id
5. 止血：示範模式已移除，正式站沒有「假生成頂著」的選項——請直接修復金鑰／額度（失敗的生成都會自動退點，夥伴不會白扣）
6. 失敗的生成會自動全額退點；若 Logs 出現 `[CRITICAL] 退點失敗（已重試 3 次，需人工補點）`，
   記下 user／points，照 4.3 對完帳後人工補點

### 4.3 點數異常（帳對不上）

帳本規則：`cost_ledger.delta` **扣點為負、退點為正**，淨消耗＝`-SUM(delta)`。
用 psql 連 Zeabur 的 PostgreSQL 跑（公開連線字串的取得方式見 2.3；查完記得把公開連線關回去）：

```sql
-- A. 全站淨消耗（應與管理頁顯示一致）
SELECT -SUM(delta) AS 淨消耗 FROM cost_ledger;

-- B. 當月每人消耗排行（消耗突增一眼看到）
SELECT user_id, -SUM(delta) AS 當月淨扣點, COUNT(*) AS 筆數
FROM cost_ledger
WHERE created_at >= date_trunc('month', now())
GROUP BY user_id ORDER BY 當月淨扣點 DESC;

-- C. 淨額為「正」的生成＝退點多於扣點，必有異常
SELECT generation_id, SUM(delta) AS 淨額
FROM cost_ledger WHERE generation_id IS NOT NULL
GROUP BY generation_id HAVING SUM(delta) > 0;

-- D. 已失敗卻沒退乾淨的生成（該人工補退的名單）
SELECT g.id, g.model_id, g.user_id, c.淨額
FROM generations g
JOIN (SELECT generation_id, SUM(delta) AS 淨額 FROM cost_ledger GROUP BY generation_id) c
  ON c.generation_id = g.id
WHERE g.status = 'failed' AND c.淨額 < 0;

-- E. 對照審計日誌：某人某天做過什麼（actor_id 填 users.id）
SELECT created_at, action, ok, error
FROM audit_log
WHERE actor_id = '<userId>' AND created_at >= current_date
ORDER BY created_at;
```

人工補點：比照程式的退點寫法，插入一筆**正 delta**、reason 註明人工補點與原因，
之後 A／B 口徑自動一致。

### 4.4 fal 月帳單對帳（每月一次）

1. fal.ai 儀表板下載當月帳單總額（USD）
2. 跑 4.3 的 B（把 `user_id` 拿掉就是全站當月淨扣點）
3. 帳單 USD × 匯率（點數校準用 31，見 docs/點數校準報告.md 檔頭）↔ 當月淨扣點（1 點≈NT$1）對比
4. 毛差大（例如 >20%）：對照 docs/點數校準報告.md「建議優先校準」表——**「偏低」的模型長期會虧**，
   改 `shared/models.ts` 的 `points` → 重新部署（啟動 `syncCatalog()` 自動同步、工作流總點數自動重算）
5. 改完點數重跑 `npx tsx scripts/audit-model-pricing.ts` 與 `npx tsx scripts/gen-model-docs.ts`，
   讓兩份文件與程式保持同步
